# 缺陷提交草稿：表库与同名树库共存时，表库不参与 RegionGroup 上限调整（PROACTIVE 失效）

> 状态：**已确证**（2026-10-20，干净 3C5D / 2.0.11-SNAPSHOT 3bbeea6，重新部署并激活）
> 关联：TDB-367「RegionGroup 积极扩容模式 PROACTIVE」；缺陷编号建议沿用 D-04（`DEFECT_CANDIDATES.md §D-04`）

## 1 标题

表模型库与同名的树模型库共存时，表库的上限 `MaxSchemaRegionGroupNum` / `MaxDataRegionGroupNum`
恒等于最小组数 (1, 2)，**永不参与** `adjustMaxRegionGroupNum()` 的调整，PROACTIVE 对该库完全失效。

## 2 环境

| 项 | 值 |
|---|---|
| 版本 | TimechoDB 2.0.11-SNAPSHOT，commit `3bbeea6` |
| 拓扑 | 3 ConfigNode + 5 DataNode，全新部署，ACTIVATED |
| 关键配置 | `schema_region_group_extension_policy=PROACTIVE`、`data_region_group_extension_policy=PROACTIVE`、`schema_region_per_data_node=3`、`data_region_per_data_node=0`、schemaRF=3、dataRF=2 |
| 数据库 | 树 `root.pg` + 表 `pg`（**同名**），另有若干非同名的对照库 |

## 3 最小复现

```sql
-- 1) 建同名的树库与表库
CREATE DATABASE root.pg;                 -- tree
CREATE DATABASE pg;                      -- table 方言（-sql_dialect table）

-- 2) 看分别的上限
SHOW DATABASES DETAILS;                  -- root.pg : MaxSchema=..., MaxData=...
SHOW DATABASES DETAILS;                  -- 表方言   : pg      : MaxSchema=1,  MaxData=2   <-- 异常

-- 3) 再触发一次调整（建任意新库），表库仍不变
CREATE DATABASE root.probe;
SHOW DATABASES DETAILS;                  -- 表方言   : pg 仍为 1 / 2
```

**实际**：表库 `pg` 恒为 `(1, 2)`；**期望**：与其他库同公式值（本例 `databaseNum=5` 时为 `(1, 12)`）。

## 4 根因（源码 + 日志 + A/B 三方自洽）

1. `ClusterSchemaInfo.enrichSchemaMap()` 以 **`path.getFullPath()` 作为结果 Map 的 key**
   （`iotdb-core/confignode/.../persistence/schema/ClusterSchemaInfo.java:679-693`）。
2. 表库 `pg` 与树库 `root.pg` 的 full path 归一为**同一字符串** ⇒ Map 中两条目互相覆盖
   （`getMatchedDatabaseSchemasByName` 先 enrich 表模型、后 enrich 树模型，`treeModelMTree` 覆盖前者）。
3. `ClusterSchemaManager.adjustMaxRegionGroupNum()` 只遍历该 Map（`:544-590`），
   表库不在 Map 中 ⇒ **永远不进入调整**，上限停留在建库默认值
   `setMaxSchemaRegionGroupNum(min)` / `setMaxDataRegionGroupNum(min)`。
4. 同一处 `databaseNum = map.size()`（`:532`）每冲突一次**少计 1** ⇒ 其余库的上限被抬高（分摊不均）。

> 说明：旧分析曾怀疑 `PartitionInfo.getRegionGroupCount()` 抛 `DatabaseNotExistsException` 后
> 被 `continue` 跳过（`ClusterSchemaManager.java:562-565`）。**该假设不成立**：
> `PartitionInfo.createDatabase()` 对树/表库都会写入 `databasePartitionTables`（`:180-184`），
> 不会抛异常。本次通过运行时日志直接证伪。

## 5 运行时日志证据

```text
# /data/mpp_test/pg_exp_1824/logs/log_confignode_all.log
[AdjustRegionGroupNum] The maximum number of SchemaRegionGroups for Database: root.d05  is adjusted to: 1
[AdjustRegionGroupNum] The maximum number of DataRegionGroups   for Database: root.d05  is adjusted to: 12
[AdjustRegionGroupNum] ... root.pg is adjusted to: 1 / 12
[AdjustRegionGroupNum] ... root.exp_tree is adjusted to: 1 / 12
[AdjustRegionGroupNum] ... root.solo_tab is adjusted to: 1 / 12
# 表库 pg / solo_tab（同名冲突后）从不出现；表库 exp_tab（无同名树库）正常出现
```

**A/B（1 秒内完成）**：

| 时刻 | 事件 | 日志 |
|---|---|---|
| 20:06:03 | 建表库 `solo_tab`（无同名树库） | `solo_tab -> 1 / 12` ✅ |
| 20:06:04 | 再建树库 `root.solo_tab`（造成同名） | `root.solo_tab -> 1 / 12`，此后 `solo_tab` **再未出现** ❌ |

**分母少计的直接证据**：7 个库、2 组同名冲突时，日志值 `1 / 12` 对应
`databaseNum = 5`（`ceil(3×5/(5×3)) = 1`、`ceil(24×5/(5×2)) = 12`），而实际库数为 7。

## 6 影响面

* 任何"树库 `root.x` + 表库 `x`"并存的部署（迁移、双模型共存、同名业务库名）都会命中；
* 表库的 RegionGroup 数被钉死在 (1, 2)，**PROACTIVE 完全失效**；
* 上限不可观测地偏低，用户会误以为已达容量上限；
* 其他库的上限被抬高，分摊不均。

## 7 修复建议

* `enrichSchemaMap` 的 Map key 加入模型维度（如 `isTableModel` 前缀或 `(db, model)` 复合键），
  或在 `adjustMaxRegionGroupNum` 中**分别遍历** `treeModelMTree` 与 `tableModelMTree`；
* `databaseNum` 的统计改为按库名去重（与 `SHOW DATABASES DETAILS` 口径一致），不要复用该 Map 的 size；
* 补 IT：建 `root.x` + 表 `x` 后断言两条目上限都等于公式值（现有 `IoTDBDatabaseIT` 只"触发"不"断言值"）。

## 8 修复验证点

1. 表库 `pg` 的 `MaxSchemaRegionGroupNum` / `MaxDataRegionGroupNum` 等于同条件其他库的公式值；
2. `[AdjustRegionGroupNum] ... Database: pg` 出现在 ConfigNode 日志；
3. `databaseNum` 与 `SHOW DATABASES DETAILS` 列出的普通库数量一致；
4. 写入 4 个 slot 后 `DataRegionGroupNum` 能增长到 `min(K, 上限)`。

## 8.5 最新 master 复现（2026-10-20 夜间全量轮）

在 **master `029a333b`（2026-10-20 22:12 构建）** 的新部署上复现，说明该缺陷**未被修复**：

* `PG-SMK-05`（表模型 4 个 slot 逐步扩容）：写入第 2/3/4 个设备后
  `SchemaRegionGroup` 恒 **1**、`DataRegionGroup` 恒 **2**（期望 2/3/3 与 2/3/4）；
* 同轮 `PG-SMK-04`（树模型同口径）PASS ⇒ 只影响表库，且与同名冲突条件一致。

**影响版本**：2.0.11-SNAPSHOT（`3bbeea6` 与 `029a333` 均复现）。

## 9 规避手段（已验证）

删除同名树库后表库**立即恢复**参与调整：删 `root.pg` + 建探针库后，表库 `pg` 重新出现在
`[AdjustRegionGroupNum]` 日志（`1/12` → `1/10`）。临时规避：**避免树库 `root.x` 与表库 `x` 同名**。

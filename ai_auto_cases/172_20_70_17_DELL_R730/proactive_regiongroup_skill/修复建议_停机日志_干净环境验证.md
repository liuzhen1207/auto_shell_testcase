# 干净环境验证报告：DataNode 优雅停机时的日志噪声

> 本报告替代此前 `修复建议_停机中断日志误报.md` 的结论部分。前一份是在**升级过、多次重启过的历史集群**上采集的，
> 本次在**全新部署的干净集群**上重复实验，结论有实质变化：**ERROR 一条都没有；此前报告里的三条目标签名均未复现。**

| 项 | 内容 |
|---|---|
| 版本 | TimechoDB 2.0.11-SNAPSHOT（commit `3bbeea6`），`distribution/target/timechodb-2.0.11-SNAPSHOT-bin.zip` |
| 环境 | 全新部署：3 ConfigNode（`.7/.8/.9`）+ 5 DataNode（`.6/.7/.8/.9/.10`），`DB_DIR=/data/mpp_test/pg_clean_2011_1020_1650`，无历史数据、无重启记录 |
| 共识/副本 | IoTConsensus，数据 RF=2，元数据 RF=3 |
| 方法 | 只做**受控优雅停机**（`sbin/stop-datanode.sh`，SIGTERM），停机目标固定 `11.101.10.10`；每次记录停机前日志行数，停机后按行号窗口截取完整日志 |
| 轮次 | 3 轮：①集群空闲 ②轻负载（300 写入 + 40 查询）③6 路并行重负载（写入+查询持续） |
| 采集文件 | `dn@11.101.10.10:/tmp/clean_stop_window.log`（211 行）、`/tmp/clean_stop_heavy.log`（305 行） |

---

## 1. 结果总览

| 轮次 | 停机窗口行数 | WARN | **ERROR** | 目标签名命中 |
|---|---|---|---|---|
| ① 空闲 | 211 | 65 | **0** | **0** |
| ② 轻负载 | 577 | 62 | **0** | **0** |
| ③ 6 路重负载 | 305 | 62 | **0** | **0** |

> 结论先行：**干净环境里，优雅停机只产生 WARN，不产生 ERROR；且 WARN 全部属于"关停导致的中断"这一类。**

## 2. 干净环境可复现的 WARN（真实现象）

| 次数（重负载轮） | 签名 | 源码 | 性质 |
|---|---|---|---|
| **38** | `WARN AbstractDriverThread:70 - Executor Query-Worker-Thread-N failed to poll driver task` | `AbstractDriverThread.java:70`（`queue.poll()` 的 `catch (InterruptedException)` 里 `logger.warn(...)`） | 关停打断查询线程的 `poll`，**每次都刷 15~38 条** |
| 10 | `WARN CompactionWorker:67 - CompactionThread-N terminates because interruption` | `CompactionWorker.java:67` | 关停打断压缩线程 |
| 2 | `WARN GrpcLogAppender:299 - ...GrpcLogAppender is interrupted` | Ratis | 关停打断日志复制 |
| 1 | `WARN CommonConfig:949 - Change system status to ReadOnly! Only query statements are allowed` | 系统状态切换 | 关停设计内行为 |
| 4（空闲轮） | `WARN LogUtils:127 - APPEND_ENTRIES onError` | Ratis | 关停时 peer 断连 |
| 1（空闲轮） | `WARN GrpcUtil:246 - Timed out gracefully shutting down connection` | Ratis/gRPC | 关停清理连接 |

**共同点**：全部与 `DataNode-Shutdown-Hook` **同一毫秒级窗口**，异常类型都是 `InterruptedException`（或线程被 interrupt 后的循环退出）。

## 3. 干净环境**未复现**的签名（重要）

此前报告（历史集群）中的以下签名，在干净环境 3 轮停机中**命中数均为 0**：

| 签名 | 此前出现位置 | 干净环境 |
|---|---|---|
| `AbstractDriverThread:123 - [ExecuteFailed]` + `InterruptedException: sleep interrupted` | 历史集群 15:22:17.200 | **未复现** |
| `ERROR FragmentInstanceDispatcherImpl:329 - Interrupted when dispatching write async` | 历史集群 15:22:17.173 | **未复现** |
| `WARN IoTDBInternalLocalReporter:250 - Failed to auto create timeseries` | 历史集群 15:22:17.173 | **未复现** |
| `ERROR ProcessFunction:49 - Internal error processing openSession` + `MetadataLeaseFencedException` | 历史集群 14:05 / 14:33 | **未复现** |
| `ERROR DataNode:415 - Fail to start server: Conflict is detected in directory ...` | 历史集群 15:30 | **未复现** |

**判断**：
1. `[ExecuteFailed]` / `:329` / `reporter:250` 需要"停机瞬间正好有查询或指标写入在途"才会触发，本次 3 轮（含 6 路并行重负载）都未命中；
2. `MetadataLeaseFencedException` 与 `DataNode:415 目录冲突` 是**历史集群环境残留**（升级 + 多次手工重启导致元数据租约被 fenced、同目录二次启动），干净环境不存在；
3. 因此这三类**不能作为"优雅停机必然产生"的产品缺陷**提交，只能作为"特定条件下可达"的代码级观察。

## 4. 修复建议（范围收窄到可复现部分）

### 建议 1（主，可复现、改动最小）：关停时 `poll` 中断不打 WARN
`AbstractDriverThread.java:66-76`：

```java
try {
  next = queue.poll();
} catch (InterruptedException e) {
  logger.warn(DataNodeQueryMessages.EXECUTOR_FAILED_TO_POLL_DRIVER_TASK_FROM_QUEUE, this.getName());
  Thread.currentThread().interrupt();
  break;
}
```

问题：`stop-datanode` 时每个 Query Worker 线程都会走到这里，一次停机刷 **15~38 条 WARN**（本次实测 38 条），
与"正常关停"语义不符，且会淹没真实告警。

建议：
```java
} catch (InterruptedException e) {
  Thread.currentThread().interrupt();
  if (closed || isShutdown()) {
    logger.debug(DataNodeQueryMessages.EXECUTOR_FAILED_TO_POLL_DRIVER_TASK_FROM_QUEUE, this.getName());
  } else {
    logger.warn(DataNodeQueryMessages.EXECUTOR_FAILED_TO_POLL_DRIVER_TASK_FROM_QUEUE, this.getName());
  }
  break;
}
```

### 建议 2：同类线程统一约定（压缩/复制线程）
`CompactionWorker:67`、`GrpcLogAppender:299` 都是"terminates because interruption"，每轮停机固定刷 10~12 条 WARN。
建议统一为：**关停态下，中断类终止日志降为 INFO/DEBUG**；非关停态保持 WARN。

### 建议 3（规范层）
在日志规范中明确一条检查项：`InterruptedException` 的 WARN/ERROR 必须能区分"关停/取消"与"真实失败"，
避免每次重启产生固定数量的误导性告警。

### 曾经的"ERROR 级 + INTERNAL_SERVER_ERROR"主张——撤回
上一版报告提出"停机时在途写请求会收到 `INTERNAL_SERVER_ERROR`"。干净环境 3 轮未复现该路径；
且补全的堆栈显示历史集群那次调用方是 `IoTDBInternalLocalReporter.createTimeSeries`（内部指标上报），
**不是用户写请求**。故该主张**撤回**，不再作为缺陷提交。若日后在用户写入负载下复现，再按新证据提出。

## 5. 验证判据（修复后如何确认）

对任一 DN 执行 `sbin/stop-datanode.sh`，采集停机窗口（停机前记录行号，停机后 `tail -n +N`）：

1. 窗口内 `AbstractDriverThread:70` 条数应为 **0**（或仅 DEBUG，默认不输出）；
2. `CompactionWorker:67`、`GrpcLogAppender:299` 的 WARN 条数应为 **0**（或 INFO）；
3. 窗口内 **无 ERROR**；
4. 集群侧 `show cluster` 在停机后 60s 内恢复（DN 重新 Running），数据可查。

## 6. 复现步骤（研发可直接照做）

```bash
# 0. 干净部署 2.0.11（3CN+5DN），确认 8 节点 Running
# 1. 记录行号
B=$(wc -l < $DB_DIR/logs/log_datanode_all.log)
# 2. 优雅停机目标 DN
./sbin/stop-datanode.sh
# 3. 等待 25s 后截取窗口
tail -n +$B $DB_DIR/logs/log_datanode_all.log > /tmp/stop_window.log
# 4. 统计
grep -c ' WARN ' /tmp/stop_window.log; grep -c ' ERROR ' /tmp/stop_window.log
grep -E 'AbstractDriverThread:70|CompactionWorker:67|GrpcLogAppender:299' /tmp/stop_window.log | wc -l
```

实测期望值（当前版本）：`WARN≈62~65`、`ERROR=0`、其中 `AbstractDriverThread:70` 占 15~38 条。

## 8. 追加实验：干净环境做一次完整升级（1.3.7 → 2.0.11）

针对"ERROR 可能是升级导致"的假设，在干净环境完整跑了一次升级，专门看升级过程与升级后启动是否复现历史 ERROR。

### 8.1 实验配置
- 源集群：干净部署 1.3.7-SNAPSHOT（3 CN `.7/.8/.9` + 5 DN `.6-.10`），`DB_DIR=/data/mpp_test/pg_clean_upg13_1020_1709`；
- 升级：`pg.sh upgrade`（stop_all → overlay 2.0.11 包 → 重写 27 个配置键 → start），目标 2.0.11-SNAPSHOT（`3bbeea6`）；
- 结果：集群成功从 1.3.7 升到 2.0.11，3 CN + 5 DN 均 `Running`。

### 8.2 升级后启动窗口（dn@.10，369 行）签名统计

| 条数 | 签名 |
|---|---|
| 10 | `WARN CompactionWorker:66` |
| 1 | `WARN ActiveLoadDirScanner:84` |
| 1 | `WARN CommonConfig:988` |
| 1 | `WARN CommonConfig:670` |
| **0** | **ERROR** |

**关键签名命中数：0** —— 没有 `MetadataLeaseFencedException`、没有 `DataNodeMemoryConfig:794`、没有 `[ExecuteFailed]`、没有 `Fail to start server`。
（`DataNodeMemoryConfig` 出现的 9 条全是 INFO 级内存分配日志。）

### 8.3 配置漂移假设：不成立
历史集群那条 `DataNodeMemoryConfig:794 … table_query_device_entry_batch_size_in_bytes (96599583) exceeds …` 曾怀疑是升级带过去的 1.3 默认值。实测：
- 升级后的 `conf/iotdb-system.properties.template` 中该键为 `table_query_device_entry_batch_size_in_bytes=0`（默认）；
- 1.3.7 包内默认同样是 0。
→ 该值 96,599,583 并非升级带过去的默认值，更可能是历史集群上**人为/自动计算**产生的，与本报告主张无关。

### 8.4 本次实验的局限（必须写明）
1. **2.0 集群处于 `UNACTIVATED` 状态**：手头 license 只覆盖 1 个 ConfigNode，而集群有 3 个，激活返回 307；
   因此 schema 写被拒绝（`307: Schema write operations are not allowed until this license activates`），
   **无法在升级后施加写入/查询负载**，也就无法覆盖"停机瞬间有在途任务"这一路径；
2. 升级工具的启动步骤仍会卡在"单 CN 无多数派"（`waiting for the seed ConfigNode`），本次由人工补齐其余 2 CN + 5 DN 完成，属**工具缺陷**（`pgkit upgrade` 应先拉起全部 CN 再等待就绪）。

### 8.5 升级场景结论
> **干净环境的 1.3.7 → 2.0.11 升级未复现任何历史 ERROR**；升级过程本身只产生常规 WARN（压缩线程、配置回显）。
> 结合 §3（停机实验也未复现），可以判定：历史集群的 `MetadataLeaseFencedException`、`FragmentInstanceDispatcherImpl:329`、
> `IoTDBInternalLocalReporter:250`、`[ExecuteFailed]` 与**多次手工重启 + 该集群特有的配置/运行状态**相关，
> **不应作为"升级必然导致"的缺陷提交**。

### 8.6 仍然成立、可提交的部分
| 项 | 证据 | 建议 |
|---|---|---|
| 停机刷 15~38 条 `WARN AbstractDriverThread:70 - failed to poll driver task` | §2，干净环境 3 轮稳定复现 | 关停时降为 INFO/DEBUG（§4 建议 1） |
| 停机刷 10 条 `WARN CompactionWorker:67 - terminates because interruption` | §2 | 同上（§4 建议 2） |
| 升级工具单 CN 启动死锁 | §8.4 | 工具侧修复：先起全部 CN 再等待 leader |

### 8.7 若要彻底闭环历史 ERROR，需要补的条件
1. 一个覆盖 3 CN 的 license（否则升级后集群只读，无法加载）；
2. 在升级后集群上施加持续写入 + 长查询负载，再执行停机，观察是否出现 `[ExecuteFailed`] / `:329`；
3. 或提供历史集群的完整 `conf/`（尤其是那次出现 96,599,583 的配置来源），以便精确复现。

## 2 关键前提：1.3 的激活是"逐机 license + .env"

1.3.7 **不接受** 2.0 线内置的 `03` 试用码（`< 2.0.10.1` 不支持），必须用 `00/01` 正式码。
正式码按**每台机器自己的 node_uuid** 签发，所以种入方式必须是：

```
每台机器：<license_2026>/license  →  <DB_DIR>/activation/license
          <license_2026>/.env      →  <DB_DIR>/.env        # node_uuid 必须与该机 license 配对
```

一次性把某一台的 license 复制给全部 5 台（节点 uuid 不匹配）**不会**激活成功——
这是 10-21 上午前两次尝试失败的真正原因，已修正为 harness 的目录形态支持：

```bash
# conf/cluster.pg_upg13_iot.conf
LICENSE_CODE=                       # 空：不用 2.0 的 03 码
LICENSE_SRC=/data/mpp_test/license_2026   # 目录：每台机器各自的 license + .env
```

`cluster.ensure_license()` 现在支持 `LICENSE_SRC` 指向目录（H-40）。

## 5 过程中暴露的 harness 问题

| 编号 | 问题 | 处置 |
|---|---|---|
| **H-40** | `ensure_license` 只会把单个 license 文件复制给所有机器，1.3 按 node_uuid 绑定 ⇒ 永远无法激活 | 支持 `LICENSE_SRC` 指向**目录**：每台机器取自己的 `license` + `.env`；已实测激活成功 |
| **H-41** | post 阶段启动时可能撞上 1.3 残留 java 进程未完全退出（`Failed to lock storage ... already locked`），`_wait_seed` 10 分钟后误报"seed ConfigNode did not come up" | 本轮由人工接管：确认进程退出后 2.0 自行起来；后续应在 `assert_stopped` 之后再加一次"端口 + 锁文件"双确认，并把 801 认证失败也视为"已应答" |

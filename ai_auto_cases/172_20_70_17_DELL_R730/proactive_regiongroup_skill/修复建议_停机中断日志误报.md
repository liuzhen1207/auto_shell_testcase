## 1. 现象

DataNode 正常关停（`DataNode-Shutdown-Hook`）时，同一毫秒级窗口内打出两类 **WARN + 完整异常栈**，但实际都是"关停把等待中的线程打断"，并非执行失败：

## 2. 根因（已定位到代码）

### 2.1 `AbstractDriverThread` 把中断当失败打印
文件：`iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/execution/schedule/AbstractDriverThread.java`

- 第 83 行 `catch (Exception e)` 捕获 `execute(next)` 抛出的一切异常；
- 进入 `else` 分支（第 123 行）无条件 `logger.warn(DataNodeQueryMessages.EXECUTEFAILED, rootCause)`；
- `InterruptedException` 不属于前面分支（CorruptedTsFile / IoTDBRuntimeException / IoTDBException / DateTimeParseException），于是落到 `else`，被当作"内部错误"打成 WARN + 栈，并 `scheduler.toAborted(...)`。

注意：第 70~76 行的 `queue.poll()` 中断**已经**被单独处理（打 poll 失败日志后 `interrupt()` 并 break），说明"中断是关停"这一语义在代码里是被认知的，只是 `execute()` 路径漏掉了。

### 2.2 哨兵线程的 sleep 不做中断处理
文件：`.../schedule/DriverTaskTimeoutSentinelThread.java` 第 66 行

```java
while (waitTime > 0L) {
  long startSleep = System.currentTimeMillis();
  Thread.sleep(waitTime);          // ← 关停时抛 InterruptedException，直接冒泡到 2.1 的 catch
  waitTime -= (System.currentTimeMillis() - startSleep);
}
```

### 2.3 指标上报把"被中断"当业务失败
文件：`iotdb-core/datanode/src/main/java/org/apache/iotdb/db/service/metric/.../IoTDBInternalLocalReporter.java` 第 250 行

```java
ExecutionResult result = COORDINATOR.executeForTreeModel(s, queryId, sessionInfo, "", partitionFetcher, schemaFetcher);
if (result.status.getCode() != TSStatusCode.SUCCESS_STATUS.getStatusCode()) {
  LOGGER.warn(DataNodeMiscMessages.FAILED_AUTO_CREATE_TIMESERIES, paths, result.status);  // ← 关停中断时也走这里
}
```

关停时 Raft 写入被中断（日志里紧跟 `RaftServerImpl:1239 Interrupted when waiting for reply`），返回非 SUCCESS → 打成 WARN。

## 3. 影响

| 维度 | 影响 |
|---|---|
| 数据/查询正确性 | **无**（异常发生在等待/上报路径，不涉及数据写入语义） |
| 运维巡检 | **有**：每次停 DN 都产生 2~4 条 WARN + 完整栈，与真实故障同样形态，容易误报/掩盖真问题（我们的回归日志检查因此判 FAIL） |
| 重启/灰度 | 每次重启都会刷出，日志噪声随重启次数线性增长 |

## 4. 修复建议（按优先级）

### 建议 1（主修，最小改动）：哨兵线程自行处理中断
`DriverTaskTimeoutSentinelThread.execute()` 的 sleep 循环：

```java
try {
  while (waitTime > 0L) {
    long startSleep = System.currentTimeMillis();
    Thread.sleep(waitTime);
    waitTime -= (System.currentTimeMillis() - startSleep);
  }
} catch (InterruptedException e) {
  Thread.currentThread().interrupt();   // 保留中断语义，供上层判断关停
  return;                               // 关停/被中断：静默退出，不再走 execute 的失败分支
}
```

### 建议 2（兜底）：`AbstractDriverThread` 的中断分支显式降级
`AbstractDriverThread.run()` 的 `else`（第 123 行）之前加一层：

```java
} else if (rootCause instanceof InterruptedException) {
  // 关停或取消导致的等待中断：保留中断标志，不按内部错误处理
  Thread.currentThread().interrupt();
  next.setAbortCause(new DriverTaskAbortedException(
      next.getDriverTaskId().getFullId(), DriverTaskAbortedException.BY_INTERRUPT));
  logger.debug(DataNodeQueryMessages.EXECUTEFAILED, rootCause);   // 或 info，视日志规范
}
```
若 `BY_INTERRUPT` 无对应枚举，可按现有 `BY_QUERY_CANCELLATION` 之类语义选择，或在 `DriverTaskAbortedException` 增加原因常量。

### 建议 3：指标上报识别关停态
`IoTDBInternalLocalReporter` 第 250 行处：

```java
if (result.status.getCode() != TSStatusCode.SUCCESS_STATUS.getStatusCode()) {
  if (isShutdown() || Thread.currentThread().isInterrupted()
      || result.status.getCode() == TSStatusCode.INTERNAL_SERVER_ERROR.getStatusCode()) {
    LOGGER.debug(DataNodeMiscMessages.FAILED_AUTO_CREATE_TIMESERIES, paths, result.status);
  } else {
    LOGGER.warn(DataNodeMiscMessages.FAILED_AUTO_CREATE_TIMESERIES, paths, result.status);
  }
}
```
（`isShutdown()` 用 DataNode 已有的生命周期标志；若无则用 `Thread.currentThread().isInterrupted()` 判定即可覆盖本次场景。）

### 建议 4（可选，规范层面）
统一约定：**"关停/取消导致的中断"不许打 WARN/ERROR**，只允许 INFO/DEBUG；可在 `ErrorHandlingCommonUtils` 或日志规范文档里落一条检查项，避免同类问题在其他线程池复现（我们已观察到 `GrpcLogAppender`、`CompactionWorker` 也是同族形态）。

## 5. 验证方法

1. **复现**：任一 3 CN + 5 DN 集群，对某台 DN 执行正常停机（`sbin/stop-datanode.sh` 或 `kill -TERM`），观察该机 `logs/log_datanode_all.log`：当前版本会在关停钩子后出现上述两条 WARN + 栈。
2. **回归判据**：修复后同一操作下，`log_datanode_all.log` 中 **不应**出现 `AbstractDriverThread:123 - [ExecuteFailed]` 与 `IoTDBInternalLocalReporter:250`（或降级为 DEBUG 且默认不输出）。
3. **自动化**：我们的 `iotdb-proactive` 技能 HA-10 用例可作回归用例（停机 + 日志卫生检查）；需要的话我可以提供打包好的执行包与判据。

## 6. 风险与备选

- 风险：若把 `InterruptedException` 一律降级，可能掩盖"业务代码自己 interrupt 导致任务异常终止"的真实问题。**建议只对"关停窗口内 + 中断来自等待原语"的情况降级**（建议 1 由哨兵线程自己吞掉中断，天然满足这一限定）。
- 备选：不改代码，改为在日志规范里明确"WARN `[ExecuteFailed]` 后跟 `InterruptedException` 视为关停噪声"，由监控侧过滤；但这会把噪声判定责任推给使用方，不推荐。

## 8. 补充复核（2026-10-20）：同一停机瞬间**也有 ERROR**，而且会向客户端返回内部错误

上次报告只举了 WARN，复核 `dn@11.101.10.8` 的 `log_datanode_all.log` 后确认：**同一毫秒级停机窗口内还有 1 条 ERROR**，且其代码路径**把中断映射成 `INTERNAL_SERVER_ERROR` 返回给客户端**。

```

java.lang.InterruptedException
    at java.base/java/lang/Object.wait(Native Method)
    at ...AsyncPlanNodeSender.waitUntilCompleted(AsyncPlanNodeSender.java:121)
```

源码（`FragmentInstanceDispatcherImpl.java` 第 327~334 行）：

```java
} catch (InterruptedException e) {
  Thread.currentThread().interrupt();
  LOGGER.error(DataNodeQueryMessages.INTERRUPTED_WHEN_DISPATCHING_WRITE_ASYNC, e);   // ← ERROR 级日志
  return immediateFuture(new FragInstanceDispatchResult(
      RpcUtils.getStatus(

```

**影响升级**：这不只是日志噪声——关停时在途的写请求会收到 `INTERNAL_SERVER_ERROR: Interrupted errors ...`，而不是"节点正在关停，请重试其它副本"这类**可重试**语义。客户端若按"内部错误"处理（不重试），会表现为**停机期间偶发写入失败**。

### 8.2 同一路径的 WARN 也有同样的状态传播问题
`AbstractDriverThread.java:123` 打出 WARN 后执行 `next.setAbortCause(new DriverTaskAbortedException(..., BY_INTERNAL_ERROR))` —— 同样把"关停中断"归因为内部错误，可能上传为内部错误状态。

### 8.3 修复建议追加（建议 5）
```java
} catch (InterruptedException e) {
  Thread.currentThread().interrupt();
  if (isShutdown()) {                      // 或 DataNode 生命周期标志 / 中断来自等待原语
    LOGGER.info(DataNodeQueryMessages.INTERRUPTED_WHEN_DISPATCHING_WRITE_ASYNC, e);
    return immediateFuture(new FragInstanceDispatchResult(
        RpcUtils.getStatus(TSStatusCode.SERVER_SHUTTING_DOWN, "Node is shutting down")));  // 可重试语义
  }
  LOGGER.error(DataNodeQueryMessages.INTERRUPTED_WHEN_DISPATCHING_WRITE_ASYNC, e);
  ...原逻辑...
}
```
若 `SERVER_SHUTTING_DOWN` 不存在，可复用现有的可重试状态码（如 `SYSTEM_READ_ONLY` / `NEED_RETRY` 一类），关键是把"关停中断"与"真内部错误"区分开。

## 10. 基于完整堆栈的更正（2026-10-20，重要）

补全堆栈后，**第 8 节的严重级推断需要下调**，特此更正，避免让研发按错误前提定位。

### 10.1 S3 的 ERROR 来自"内部指标上报"，不是用户查询

完整栈自下而上是：

```
... FragmentInstanceDispatcherImpl.dispatch  →  ClusterScheduler.start
... QueryExecution.start  →  Coordinator.executeForTreeModel
... IoTDBInternalLocalReporter.createTimeSeries(IoTDBInternalLocalReporter.java:247)
```

即：被中断的那次写，是 `IoTDBInternalLocalReporter` 为写 `root.__system.metric.*` 而发起的内部写入，
**不是用户发起的写请求**。它随后被上报方自己捕获，才产生 S4 那条 `WARN Failed to auto create timeseries`。

**结论更正**：本次证据**不能**证明"用户写请求在停机时会收到 `INTERNAL_SERVER_ERROR`"。
`FragmentInstanceDispatcherImpl:329` 的 catch 确实会返回 `INTERNAL_SERVER_ERROR`，但本次命中的调用方是内部指标，
影响仅限"指标丢一个采样点 + 两条日志"。

### 10.2 但仍需研发确认的一点（保留，降级为待确认）

若**用户查询**在关停窗口内走到同一个 catch，客户端会收到 `INTERNAL_SERVER_ERROR: Interrupted errors ...`。
本次未复现到用户路径，因此这属于**待确认风险**，不是已证实的缺陷——请研发判断该 catch 是否应按"关停可重试"处理。

### 10.3 S1/S2 是另一类问题，值得单独看（P2 候选）

完整栈显示失败点在**鉴权阶段**：

```
openSession → SessionManager.login → AuthorityChecker.getUserId
  → ClusterAuthorityFetcher.getUser → failIfMetadataLeaseFenced
  → MetadataLeaseFencedException: Metadata lease is fenced. The local metadata cache is unavailable.
```

含义：DataNode 元数据租约被 fenced 期间，**任何客户端 openSession 都会失败**，且以 thrift `Internal error processing openSession` 的形式返回（ERROR 级）。
出现时间 14:05:18 / 14:33:24，正是节点重启恢复窗口。

**待研发确认**：
1. 该窗口内 openSession 失败是否预期？
2. 若预期，返回给客户端的应是**可重试状态**（如"节点恢复中，请重试/换节点"），现在是无差别 `Internal error`，客户端无法区分"重试就好"与"真故障"；
3. 若不符合预期，这条比日志噪声更值得修（影响客户端连接成功率）。

### 10.4 定级更新

| 项 | 原建议 | 更正后 |
|---|---|---|
| 关停中断日志（WARN/ERROR） | P3 日志质量 | **保持 P3**（确认无用户可见影响） |
| 用户写路径可能回 `INTERNAL_SERVER_ERROR` | P2 | **待确认**（本次未复现到用户路径） |
| `openSession` 因元数据租约 fenced 失败 | — | **P2 候选，需研发确认** |
| `DataNode:415 目录冲突启动失败` | 我方残留 | 不变（非产品问题） |

### 10.5 给研发的一句话
> 关停时确实会打 1 条 ERROR（`FragmentInstanceDispatcherImpl:329`）+ 2 条 WARN，但完整栈显示它们来自**内部指标上报**（`IoTDBInternalLocalReporter.createTimeSeries`），不是用户写请求，因此只影响指标采样与日志；真正值得确认的是同一台机上 `openSession` 因 `MetadataLeaseFencedException` 直接失败的问题（见 §10.3）。

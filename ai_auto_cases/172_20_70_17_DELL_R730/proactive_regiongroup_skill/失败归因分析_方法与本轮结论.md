## 1 方法：五步归因法

### Step 0 期望值来源审查

| 等级 | 来源 | 可用于判缺陷 |
|---|---|---|
| A | 需求/设计文档明文、源码公式、产品自报值 | ✅ |
| B | 现有 IT 断言、历史版本行为 | ⚠️ 仅旁证 |
| C | 用例作者按直觉写的期望 | ❌ 先怀疑用例 |

本轮 89 个 FAIL 里 52 个栽在 C 级期望或解析缺陷上（H-19 / H-22b / H-26~H-28）。

### Step 1 同签名聚类

一条签名（现象 + 期望 + 实测同形）= 一类问题。26 个用例报同一签名 = **1 个缺陷**。

### Step 2 单变量对照

同集群、同时刻、只改一个变量：树库 vs 表库、设备级 vs 测点级、触发前 vs 触发后。

### Step 3 机制定位

三条线索必须自洽：**源码路径** + **运行时日志**（产品自打的计算值）+ **产品自报值**（`SHOW`）。

### Step 3.5 触发条件定位（本轮新增的关键一步）

"能复现"不等于"知道触发条件"。D-04 的 26 例在固定形状下复现，但**单独建表库不复现**；
把"裸建表库"作为对照臂才定位到**同名冲突**这个必要条件。**没有对照臂就会把缺陷范围写错。**

### Step 4 判定矩阵

| 期望来源 | 可复现 | 机制自洽 | 判定 |
|---|---|---|---|
| A | ✅ 稳定 | ✅ | **产品缺陷**，提单 |
| A | ✅ 稳定 | ❌ | 产品缺陷（机制待定），附实验方案 |
| A | ⚠️ 偶发/不复现 | — | 记录，**不登记** |
| B/C | 任意 | — | 用例/判据修正，**不登记** |
| 行为变更（文档未写） | ✅ | ✅ | **文档/RN 缺口**，不记功能缺陷 |

### Step 5 证据封存

`result.json:checks[i]` + 日志原始行 + 可重放 SQL，三者缺一即视为无效结论。

## 2 逐类分析

### 2.1 D-04（已确证）表库与同名树库共存 ⇒ 表库永不参与上限调整

**现象**：表库 `pg` 的 `MaxSchemaRegionGroupNum / MaxDataRegionGroupNum` 恒为最小组数 (1, 2)，
写 4~5 个 slot、重启、换策略、主动触发调整都不变；同条件树库正常。

**根因（源码 + 日志 + A/B 三方自洽）**

* `ClusterSchemaInfo.enrichSchemaMap()` 用 `path.getFullPath()` 作结果 Map 的 key（`:679-693`）；
* 表库 `pg` 与树库 `root.pg` 的 full path 归一为同一字符串 ⇒ 两条目**互相覆盖**
  （表先插入、树后覆盖）；
* `ClusterSchemaManager.adjustMaxRegionGroupNum()` 只遍历该 Map（`:544-590`）⇒ 表库不在其中，
  **永远不被调整**，上限停在建库默认 `setMax*(min*)`；
* `databaseNum = map.size()` 每冲突一次少计 1 ⇒ 其余库的上限被**抬高**（分摊不均）。

> 旧文档"D-04 因 `getRegionGroupCount` 抛 `DatabaseNotExistsException` 被跳过"的解释**已废弃**：
> `PartitionInfo.createDatabase()` 对树/表库都写 `databasePartitionTables`（`:180-184`），不会抛异常。

**干净环境实锤（2026-10-20，3C5D 2.0.11 全新部署并激活）**

| 库 | 同名树库存在 | Max Schema | Max Data | 出现在 `[AdjustRegionGroupNum]` 日志 |
|---|---|---|---|---|
| 表 `exp_tab` | 否 | 1（=公式） | 12（=公式） | ✅ |
| 表 `solo_tab`（先建） | 否 | 1 | 12 | ✅ 20:06:03 |
| 树 `root.solo_tab`（后建） | — | 1 | 12 | ✅ 20:06:04 |
| 表 `solo_tab`（冲突后） | **是** | 1 | 12（不再更新） | ❌ 20:06:04 起消失 |
| 表 `pg` | **是**（树 `root.pg`） | **1** | **2** | ❌ 全程未出现 |
| 树 `root.pg` / `root.d05` / `root.exp_tree` | — | 1 | 12 | ✅ |

* A/B 在 **1 秒**内完成：`20:06:03 solo_tab -> 1/12` → 建 `root.solo_tab` → `20:06:04 root.solo_tab -> 1/12`，`solo_tab` 此后再未出现。
* 分母少计的证据：7 个库、2 组同名冲突时日志值 `1/12` 对应 `databaseNum=5`（`ceil(3×5/(5×3))=1`、`ceil(24×5/(5×2))=12`）。

**影响**：任何"树库 `root.x` + 表库 `x`"并存的用户，表库上限恒为 (1, 2)、
`DataRegionGroupNum` 永远到不了 3；其余库上限被抬高。

**判定**：产品缺陷（已确证）。建议提单标题：
「表库与同名树库共存时，表库不参与 RegionGroup 上限调整（PROACTIVE 失效）」。

### 2.2 D-05（撤销）测点级 `select count(*)` 空集

**干净环境复现（同一份数据）**

```text
select count(*) from root.d05.dev1     -> |count(root.d05.dev1.s1)| 1   （设备级：每测点一列）
select count(*) from root.d05.dev1.s1  -> Empty set                    （测点路径下无子测点）
select count(s1) from root.d05.dev1    -> 1                            （正确写法）
select s1     from root.d05.dev1.s1    -> Empty set                    （FROM 为测点路径，1.x/2.x 同）
select s1     from root.d05.dev1       -> 1.0                          （数据本身可查）
```

**结论**：2.x 的 `count(*)` = "FROM 路径下**各测点**的行数"（H-31）。路径落到**测点**时没有子测点，
返回空集是**语义一致**的结果，不是"写后不可读"。

**处置**：harness 新增 `PgApi.count_series()`（`select count(<sensor>) from <db>.<device>`），
替换 20 处测点级 `count_rows(...)`（`cases.py` 1 处、`cases_msr.py` 19 处），
`selftest` 764 项全过；详见 `HARNESS_FINDINGS.md` H-37。

**建议**：RN 补一条 1.3→2.0 兼容性提示（同一 SQL 在 1.3 返回行数、在 2.0 返回空集）——文档缺口，不记功能缺陷。

### 2.3 HA-10 停机瞬间 `[ExecuteFailed]`（不登记）

`DriverTaskTimeoutSentinelThread.execute(:66)` 抛 `InterruptedException: sleep interrupted`，
由 `DataNode-Shutdown-Hook` 触发；`FragmentInstanceDispatcherImpl:329` 的 ERROR 来自内部写
（`IoTDBInternalLocalReporter.createTimeSeries`），不是用户写入。
干净环境 3 轮停机（空闲/轻载/重载）+ 1.3→2.0 升级轮：目标签名 0 命中、ERROR 0 条 ⇒ 不可复现，不登记。

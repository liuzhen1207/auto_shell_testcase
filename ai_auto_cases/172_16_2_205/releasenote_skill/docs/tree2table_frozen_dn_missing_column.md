# 【缺陷候选】DN 失联期间新建序列，树转表视图会静默永久丢列

| 项目 | 内容 |
| --- | --- |
| 需求 | TDB-343 树转表视图自动扩列 |
| 设计文档 | `docs/913` §4.2.3「处于隔离状态的 DN…」、§4.3.3「尽力而为」 |
| 复现版本 | **RC1**: 2.0.13.1 / `ab6d3de`；**RC2**: 2.0.13.1 / `83183d0`（两个版本均复现） |
| 复现概率 | 约 **50%**（4 次观测：2 次丢列、2 次补上） |
| 关联用例 | RN-204（稳定断言 + 丢列观察项） |
| 影响 | 用户建序列成功、视图却永久缺该列，且**日志无任何提示** |

---

## 一、现象

1. 视图已开启 `auto_sync_schema=true`；
2. 用 `kill -STOP` 冻结一台 DN（模拟失联/无响应）；
3. 冻结期间在视图 prefix 下 `create timeseries`（返回成功）；
4. `kill -CONT` 恢复，集群回到 8/8；
5. **该测点对应的列没有出现在视图里**，等待 120 秒仍不出现；
6. 之后新建的其他测点能正常补列（说明功能本身没坏）。

即：**这一次建序列的扩列被静默丢弃，且没有补偿机制**。

## 二、复现步骤（可直接执行）

```bash
# 环境：172.16.2.205 集群，DN6=172.16.2.6
CLI=/data2/iotdb/v20131rc1_1030_ab6d3de/sbin/start-cli.sh
Q() { $CLI -h 172.16.2.2 -p 6667 -u root -pw 'TimechoDB@2021' -sql_dialect table -e "$1"; }
T() { $CLI -h 172.16.2.2 -p 6667 -u root -pw 'TimechoDB@2021' -sql_dialect tree  -e "$1"; }

T "create database root.d1";                       # 或 Q "create database d1"
T "create timeseries root.d1.dev01.s1 double"
Q "create view d1.v1(dev string tag) with(auto_sync_schema = true) as root.d1.**"

PID=$(ssh root@172.16.2.6 "pgrep -f com.timecho.iotdb.DataNode | head -1")
ssh root@172.16.2.6 "kill -STOP $PID"; sleep 12
T "create timeseries root.d1.dev01.frozen_col double"   # 返回 successfully
ssh root@172.16.2.6 "kill -CONT $PID"
# 等集群回到 8/8，然后反复检查：
Q "desc d1.v1"          # 约 50% 的情况看不到 frozen_col
T "create timeseries root.d1.dev01.after_col double"     # 后建的能正常补列
```

## 三、实测数据

| 轮次 | 冻结期间建序列 | 恢复后 10s | 30s | 60s | 120s | 之后新建测点 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 成功 | 1 列 | 1 | 1 | 1 | 正常 |
| 2 | 成功 | 0 | 0 | 0 | **0（永久缺列）** | 正常 |
| 3 | 成功 | 1 列 | 1 | 1 | 1 | 正常 |
| 4 | 成功（返回空但已生效） | 0 | **0** | 0 | 0 | 正常 |

## 四、日志证据

冻结窗口内，4 台健康 DN 的 `log_datanode_all.log` 中与 `add view column / tree_to_table / tree2table` 相关的日志行数均为 **0**：

```
172.16.2.2 相关日志行数=0
172.16.2.3 相关日志行数=0
172.16.2.4 相关日志行数=0
172.16.2.5 相关日志行数=0
```

即：**丢列过程没有任何 WARN/ERROR**，用户与运维都无从发现。

## 五、与文档的差异

设计文档 §4.2.3 关于隔离状态下的扩列：

> - 单机模式：如果 apply log 的时候正好碰到隔离状态，那么此次给视图扩列失败；视图永远缺少该列，会在专门的日志文件中记录；
> - 集群模式（DN 数量 >=3）：DN 上的 follower 和 leader 存在一个健康的节点，apply log 的时候都会去触发扩列，**所以一个 DN 处于隔离状态不影响视图去自动扩列**。

实测在 3C5D（远多于 3 个 DN）下，**仍会出现丢列**，与「集群模式不影响扩列」的表述不符；且「会在专门的日志文件中记录」也未见任何日志。

## 六、可能原因（供研发参考，未验证）

- 建序列请求被路由到正在被冻结的 DN（或其 leader 副本），该副本在恢复后 apply log 时，本地树转表索引/CN 连接处于异常态，扩列 RPC 失败且被"尽力而为"吞掉；
- 也可能与 §4.3.3 的 OVERLAP 重试机制相关：冻结期间同表 procedure 卡住，重试 4 轮后返回失败，DN 仅记日志——但本次未观察到日志。

## 七、建议

1. **优先确认**：集群模式（≥3 DN）下单 DN 失联是否应保证扩列不丢？若应保证，请定位为何丢列；
2. **可观测性**：无论是否修复，建议在丢列时记录 WARN（含 database、视图名、缺失列名，遵循"不暴露原序列全名"的约束）或落一个计数指标；
3. **补偿机制**：DN 恢复（从失联/隔离恢复）后触发一次补扫（`detectMissingColumnsAfterCreation` 已有实现，可复用）；
4. **文档**：若确认属于「尽力而为」的正常语义，请在需求/手册中明确写出「节点失联期间的扩列可能丢失，需人工补列」，并给出补救命令（`alter view ... add column`）。

## 八、对应自动化

- `RN-204`（慢组）：断言「冻结期间写入成功 + 恢复 8/8 + 之后新建测点补列正常」，并对丢列做**观察记录**（不判定 FAIL，避免 flaky）；
- 若研发确认属于缺陷并修复，可把 RN-204 的观察项升级为硬断言（应补上）。

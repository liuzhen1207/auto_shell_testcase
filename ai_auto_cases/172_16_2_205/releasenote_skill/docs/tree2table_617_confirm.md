## 〇、研发确认结论（2026-11-06）

> **只有创建树转表视图的时候，才会因为列类型冲突去返回失败；其他情况都默认忽略。**

据此确定的产品口径：

| 路径 | 期望行为 | 对应用例 |
| --- | --- | --- |
| 创建树转表视图（未声明 Field 列） | 检测到同名小写冲突 → **创建失败，返回 617** | RN-146 |
| 创建后再新增冲突测点（含 INSERT 自动建序列、显式 CREATE TIMESERIES、模板扩展） | **忽略**，不新增列，写入成功，仅记 warn | RN-145 |
| `auto_sync_schema` 由 false 改为 true 的补扫 | **忽略**冲突，属性切换成功，不报错 | RN-147 |
| 建视图后补扫（`detectMissingColumnsAfterCreation`） | **忽略**冲突，仅记 warn | RN-147（同一路径） |
| 开启属性后新增的普通测点 | 正常补列（功能不受冲突影响） | RN-147 |

补充实测结论（与上述口径一致、但文档未提）：

- **建视图时的列检测与 `auto_sync_schema` 开关无关**：即使不写 `with(auto_sync_schema=true)`，
  只要视图未声明 Field 列，创建时同样会扫描 prefixPath 并对冲突报 617。
- 因此 617 属于「建视图时的自动列推导」约束，不是「自动同步」开关的约束。

下面的 Q1/Q2 已由研发确认关闭；Q3~Q5 仍建议作为体验优化项跟进（不阻塞本版本）。

---

## 一、一句话问题

同一个「测点小写冲突」场景，**建视图时直接报 617 失败**，而**建好视图后新增测点只记 warn 并跳过**；需求文档只写了后者的处理方式，没写前者。请确认这是否是预期设计。

---

## 二、现象与复现

### 2.1 建视图：硬失败（617）

```sql
create database db1;
create timeseries root.db1.dev01.s1 double;
create timeseries root.db1.dev02.S1 int32;      -- 与 s1 仅大小写不同、类型也不同

create view db1.v1(dev string tag) with(auto_sync_schema = true) as root.db1.**;
```

实际返回：

```
617: The measurements s1 and S1 share the same lower case when auto detecting type, please check
```

视图创建**整体失败**，一列都没有生成。

### 2.2 先建视图、后新增冲突测点：软跳过

```sql
create database db2;
create timeseries root.db2.dev01.s1 double;
create view db2.v1(dev string tag) with(auto_sync_schema = true) as root.db2.**;   -- 成功，列 s1

create timeseries root.db2.dev02.S1 int32;   -- 成功，视图不新增列，仅 warn
desc db2.v1;                                 -- s1 仍为 DOUBLE，未新增列
```

写入不报错，视图结构保持不变，符合需求文档 3.2.2 第 1 条。

### 2.3 同场景第三种表现：建视图后的补扫会「静默吞掉」

视图建好之后（或把 `auto_sync_schema` 从 false 改成 true 时）会触发一次补扫，
若补扫过程中出现同类冲突，**既不报错也不提示用户，只记 warn 并返回空列**。

---

## 三、需求文档怎么写的

需求文档 3.2.2 只描述了「**新增序列**」这一条路径：

> 开启配置项 `auto_sync_schema = true` 后，去新增序列时，取序列名的小写，和视图中已有的列（视图中的列名只能是小写）进行对比：
> 1. 如果在视图中发现存在该序列名，那么不能新增列，记一条 warn 日志；（不会在日志里面暴露原序列）
> 2. 如果发现视图不存在该列，那么接着去遍历视图中列的 original name……说明同一条序列已经被引用过了，那么也不允许新增列……

§3.4 场景 3 补充：

> 除类型冲突外，若新增测点与已有列仅大小写不同（如 S1 与 s1），同样按冲突处理并跳过该列。

与「建视图」相关的只有两句：

> （视图中的列名只能是小写）

> b. 如果在 viewColumnDefinition 中指定了 Field 列和其数据类型……这种写法是为了规避同名测点类型冲突的情况

**文档缺口**：
1. 建视图时若 prefixPath 下已存在 `s1` 与 `S1`，是拒绝还是跳过 —— 未定义；
2. 拒绝了之后用户如何恢复 —— 未定义；
3. 建视图后的补扫失败是静默的 —— 未定义（用户无法感知"我这列为什么没进来"）。

设计文档 `docs/913` 全文无 `617`、无「小写冲突」相关描述。

## 四、代码现状（三处不同处理）

| 触发路径 | 入口 | 冲突时行为 |
| --- | --- | --- |
| 建视图（未声明 Field 列） | `CreateTableViewProcedure` → `TreeDeviceViewFieldDetector.detectFieldsForCreation()` | 检测失败 → `setFailure` → 客户端收到 **617** |
| 建视图后补扫 / 开启属性时补扫 | `detectMissingColumnsAfterCreation()` | 检测失败 → `LOGGER.warn` 后 **return 空列**，用户无感知 |
| 新增序列触发加列 | `AddViewColumnProcedure` → `detectFieldTypesForColumnAddition()` | 加列 procedure 失败 → DN 记 warn，**写入继续** |

同一份检测逻辑（`MEASUREMENT_NAME_CONFLICT` / code 617），三个调用方三种失败处理方式。

## 五、需要确认的问题

### Q1（核心）建视图报 617 是否为预期行为？

- 选项 A：预期。视图列名必须唯一小写，无法自动生成两列，宁可失败也不静默丢列。
- 选项 B：非预期。应与增量路径一致，跳过冲突列 + warn，视图照常建成。
- 选项 C：预期但需优化：报错改为更具体的提示（指出哪两个测点冲突、建议如何修复）。

> 我的建议：A 或 C。理由是"建视图时静默少一列"比"直接报错"更难排查；但当前错误信息只提示 `please check`，用户不知道该怎么办，建议至少补上修复指引。

### Q2 三种失败处理是否需要统一？

目前建视图失败、补扫吞掉、增量 warn，同一冲突三种表现。请确认：
- 建视图后的补扫失败是否应该给用户可感知的提示（如 `show create view` 中体现"待补齐列"，或专门日志文件）？
- 是否属于「尽力而为」的合理设计，无需改动？

### Q3 显式声明 Field 列是否是官方推荐的规避手段？

实测确认：视图显式声明 `s1 FIELD DOUBLE` 时，冲突检测走另一条路径，可以正常建视图（`detectFieldTypes` 只解析未声明类型的列）。
- 若是官方手段，请确认是否写进用户手册（当前手册只写了"指定类型不一致时查不出来"）；
- 若不是，用户踩到 617 后的标准修复步骤是什么？

### Q4 「建视图后的补扫吞掉」是否会造成永久缺列？

若补扫时因冲突失败并返回空列，后续是否还有机会补上？
- 是否有重扫机制（例如重新执行 `ALTER VIEW ... SET PROPERTIES auto_sync_schema = true`）？
- 还是必须 `DROP VIEW` 重建？

> 这一点影响用户自救路径，建议明确。

### Q5 报错信息是否需要包含修复指引？

当前：`617: The measurements s1 and S1 share the same lower case when auto detecting type, please check`

建议改为类似：
```
617: 测点 root.db1.dev01.s1 与 root.db1.dev02.S1 小写形式相同，无法自动生成视图列。
     请在视图定义中显式声明列类型（如 s1 FIELD DOUBLE），或删除/重命名其中一个测点后重试。
```

同时请确认：报错信息里带原始序列全名，是否与需求「日志不暴露原序列」的约束冲突（当前是返回给客户端的错误，不是日志）。

## 六、影响面

| 用户场景 | 影响 |
| --- | --- |
| 历史库中同一设备/不同设备存在 `s1` / `S1` 这类测点，首次给该 prefix 建自动同步视图 | **建视图直接失败**，需先清理数据或显式声明列 |
| 建好视图后新设备写入同名不同大小写测点 | 写入正常，视图少一列（符合文档） |
| 从 false 切到 true（开启属性） | 补扫失败静默，用户以为开启了但列没补齐 |

第 1 条和第 3 条是文档没覆盖、且用户最可能踩到的。

## 一、待确认的问题

1. 特权账户（root / 安全管理员）**远程**登录时被锁定，是否属预期设计？（需求只承诺"本机豁免"）
2. 发生误锁时，现场是否接受"换客户端 IP、或登录其他 DataNode、或本机登录"作为解锁手段，还是需要新增带外解锁能力？
3. 是否需要把"被锁的范围"（哪个用户、哪个来源 IP、哪个 DN）暴露给运维（当前 822 只提示 Account is blocked）？

## 二、实测行为（用于判断风险）

### 2.1 豁免（符合需求 L128，已验证）

| 场景 | 结果 |
| --- | --- |
| 本机（DN 主机 .2）root 连续 8 次错误 → 本机正确密码 | ✅ 登录成功 |
| 本机（DN 主机 .2）security_admin（三权分立下）连续 8 次错误 → 本机正确密码 | ✅ 登录成功（`list user` 正常返回） |
| 远程锁定后，再从本机登录 | ✅ 仍成功（豁免优先于锁定） |

### 2.2 锁定范围（本次新增实测，决定风险等级）

| 场景 | 结果 | 说明 |
| --- | --- | --- |
| 205 → DN .2 连续 6 次错误，205 再登录 .2 | ❌ `822 Account is blocked` | 基线：来源 IP 被锁 |
| **换来源**：在 DN .3 上执行 CLI 登录 .2 | ✅ 成功 | 锁定不跨来源 IP |
| **换目标**：205 登录 **DN .3** | ✅ 成功 | 锁定不跨 DN |
| 本机 .2 → .2（8 次错误后） | ✅ 成功 | 本机豁免 |

**推论：锁定粒度为「用户 + 来源 IP + 目标 DataNode」三者组合。** 误锁后至少有三条现成逃生路径（换客户端、换 DN、本机登录），不影响集群整体可用性。

### 2.3 残余风险（低）

- 仅在**同一来源 IP 对所有 DN**累计到用户级阈值（`failed_login_attempts_per_user`，默认 1000）时才可能形成大面积锁定；正常运维远达不到；
- 若客户把两个阈值都调小（例如 IP 级 5、用户级 5）且只用单一客户端，才可能出现"人工无法登录"，属配置使用问题；
- `ALTER USER ... ACCOUNT UNLOCK` 需要先能登录才能执行（L152 规定只有 root / 安全管理员可执行），因此"逃生路径"是必要前提；当前实测该前提成立。

## 三、复现步骤

```bash
# 1) 确保无锁（重启目标 DN）
ssh root@172.16.2.2 "stop-datanode.sh; pkill -9 -f com.timecho.iotdb.DataNode; setsid start-datanode.sh"
# 2) 从客户端 205 连续 6 次错误
for i in $(seq 1 6); do start-cli.sh -h 172.16.2.2 -u root -pw "Wrong@$i" -e "show cluster"; done
start-cli.sh -h 172.16.2.2 -u root -pw 'TimechoDB@2021' -e "show cluster"   # → 822
# 3) 换来源（在 DN .3 上执行）
start-cli.sh -h 172.16.2.2 -u root -pw 'TimechoDB@2021' -e "show cluster"   # → 成功
# 4) 换目标（从 205）
start-cli.sh -h 172.16.2.3 -u root -pw 'TimechoDB@2021' -e "show cluster"   # → 成功
```

脚本：`auth_skill/tools/probe_q1_lock_scope.sh`、`probe_obs9_local.sh`、`probe_obs9_remote.sh`、`probe_q2_secadmin_local.sh`

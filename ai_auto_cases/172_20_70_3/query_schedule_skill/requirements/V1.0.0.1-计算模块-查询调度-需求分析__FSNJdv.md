一、需求描述
物联网场景下主要有两种典型分析负载：历史数据分析查询和实时数据查询。历史数据分析查询是时序数据库管理系统中的重要应用场景之一。通过对历史存储的海量数据进行分析，历史数据分析查询可以从多个数据维度提取有价值 这种查询通常需要对过去某一长时间段的历史存储数据进行降频采样、 聚合等操作，处理的数据体量较大，需要占用大量的系统资源，执行时间也相对较长。 实时数据查询是对新到来的数据进行查询，这类查询通常用于实时监控系统状态，并对异常事件进行实时预警，从而保障系统的正常运行。实时数据查询需要尽可能快地检测出异常或者趋势变化，并在最短时间内提供给用户或者系统管理员，从而最大程度地减少损失。
实时数据查询关注的时间范围较短，涉及的时间维度较少，使用的系统资源也较少，通常需要在毫秒级别内返回结果；而历史数据分析查询通常在较长时间范围和较高数据维度上对过去的数据进行分析，使用的系统资源较多，返回结果的时间也较长。由于实时数据查询耗时较短，因此用户通常期望其能够及时返回结果，如果实时数据查询响应延迟增加，会严重影响用户体验。由于分析型查询本身的延迟较长，用户对其的期望也相对较低，因此延迟的少量增加不会对用户的体验造成严重影响。 但是，如果不对系统的查询调度机制加以管理，实时数据查询的查询性能往往会受到历史数据分析查询的影响。例如，在目前广泛采用的线程池执行模型中，线程数量是固定的，如果所有线程都正在执行任务，那么新任务就无法被执行。如果占用执行线程的是消耗系统资源较多、执行时间较长的历史数据分析查询，那么后续到来的实时数据查询都必须长时间等待，对查询响应时间造成严重影响。为了避免这种情况，需要采用合适的调度算法来管理查询任务的执行顺序，实现对实时数据查询的优先响应。
线程池模型本质上采用的是先来先服务的调度机制，并不支持优先级调度，其本身也并不支持实现其他的调度算法。一些调度算法支持优先级调度，可以优先响应实时数据查询。但是在调度时将每个任务都视为独立的，没有考虑多个任务之间的关联关系。在并行系统中，单个查询任务可能被划分为多个子任务并行执行，像历史数据分析查询一样的复杂查询往往会被分成更多的子任务。而在时序数据库管理系统中，每个子任务的规模可能是以时间序列为单位，这与单个实时查询任务相似。如果将每个任务都视为独立的，根据任务规模来判断优先级，那么可能导致历史数据分析查询与实时数据查询被调度的优先级相同，从而影响实时数据查询的响应速度。因此，调度算法不能只考虑单个任务的规模来判断优先级，还需要考虑多个并行子任务之间的关联关系，以避免影响实时数据查询的响应速度。此外，如果调度算法只考虑优先响应实时数据查询，历史数据分析查询的性能可能会被过分影响。在时序数据库管理系统中，实时数据查询的频率通常较高且比较固定，这与传统关系数据库的查询模式存在很大不同。由于每时每刻都会有实时数据查询加入，如果在每次调度时都优先响应实时数据查询，这可能会导致历史数据分析查询任务始终得不到执行而被饿死。因此，调度算法在优先考虑实时数据查询的同时，还需要考虑如何在实时数据查询频率过高时避免历史数据分析查询的饥饿问题，确保其能有机会执行。
综上所述，时序数据库管理系统中的查询调度机制是影响查询性能的重要因素，我们需要设计一套完善的查询调度机制。

三、功能定义
功能描述
查询调度器（Query Scheduler）是数据处理系统（如数据库、数据仓库、大数据平台）的核心组件之一，其核心定位是对系统中待执行的查询任务（SQL 查询、数据检索请求等）进行统一管理、优先级排序、资源分配与执行调度，最终实现 “高效利用系统资源、保障关键查询响应速度、避免任务拥堵” 的目标。简单来说，查询调度器相当于数据系统的 “交通指挥官”，负责协调海量查询任务的执行顺序与资源占用，平衡 “执行效率” 与 “业务优先级”。
功能定义
查询子任务状态管理
功能需求：
子任务追踪： 系统需要能够追踪每个查询任务的子任务状态，包括子任务的创建、执行、完成或失败状态。
状态更新： 子任务状态的任何变化都需要及时更新，以确保系统能够反映最新的执行情况。
错误处理： 对于失败的子任务，系统需要有能力进行错误恢复或重新调度。
依赖管理： 子任务之间可能存在依赖关系，系统需要管理这些依赖，确保子任务按正确的顺序执行。
实现考虑：
状态机设计： 使用状态机模型来管理子任务的不同状态（如 Ready、Running、Blocked、Cancelled 等），并定义状态之间的转换规则。
事件驱动机制： 采用事件驱动的架构，当子任务状态发生变化时，触发相应的回调任务，更新状态并记录日志。
依赖图管理： 使用图数据结构表示子任务之间的依赖关系，调度器在调度时优先处理无依赖的子任务。
任务调度器
功能需求：
优先级调度： 调度器需要根据任务的类型（实时或历史）和紧急程度/累计执行时间来分配不同的优先级。
负载均衡： 调度器需要在多个执行资源之间平衡任务负载，以避免资源过载。
饥饿避免： 调度算法需要避免某些任务（如历史数据分析查询）因实时数据查询的高频率而饥饿。
动态调整： 调度器应能够根据系统当前的负载和任务特性动态调整调度策略。
实现考虑：
采用时间片机制，让任务可以让出执行权。
采用多级队列，每个级别对应不同的优先级。
监控系统负载，并根据实时数据调整任务的优先级和执行顺序。
查询任务队列
功能需求：
队列管理： 系统需要能够管理多个任务队列，每个队列对应不同的优先级或任务类型。
任务排序： 队列需要能够根据任务的优先级和到达时间等因素对任务进行排序。
队列监控： 系统需要监控队列的长度和任务的等待时间，以便于调度器做出决策。
队列扩展性： 队列应能够灵活扩展，以适应不同规模的查询负载。
实现考虑：
使用优先级队列来管理不同优先级的任务。
实现一个动态调整的队列系统，可以根据任务类型和系统负载自动调整队列的数量和大小。
提供队列长度和等待时间的实时监控功能，以便调度器可以做出及时的调整。

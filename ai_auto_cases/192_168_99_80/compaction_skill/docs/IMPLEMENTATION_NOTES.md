# CO-35 ~ CO-42 实现偏差与首跑关注点（如实记录）

> 这 8 条用例是按 `docs/OFFICIAL_COVERAGE.md` §4.2 的规格实现的，但**规格是设计意图、实现要迁就环境**。
> 下面是实现者主动报告的偏差与"可能误判"清单（**首跑 FAIL 时先读这里**，避免把构造问题当成产品缺陷）。
> 每条用例的权威判据在**脚本头部注释**里。

## 一、逐条偏差

| 用例 | 偏差 | 为什么 | 首跑怎么判 |
| --- | --- | --- | --- |
| **CO-35** 目标文件拆分 | 默认 target 用**动态值** `floor(0.8 × 最小 region 源字节)`，不是官方 3072；用 **6 设备**而非单设备 | ① 本环境单 L0 仅 3~20KB，官方 3072 会让计划数被"产物数 ≤ 源文件数"截断 ⇒ 不真拆分、TsFile 不下降 ⇒ **必然误判"未推进"**；② 设计文档明确拆分发生在 `endChunkGroup`（设备写完）⇒ 单设备永远只有 1 个产物 | 想按官方数值复现：`CO35_TARGET=3072`（此时用例会 WARN 标注公式被截断）。若判"场景未成立"，先看是不是 6 设备被拆成了 6 个 region（每 region 1 设备）⇒ 需调 `CO35_DEVS` |
| **CO-37** 对齐分组合并 | 模板设备放在 **d2**（d1 走显式 12 列 DDL） | 同一设备上"模板 8 列"与"显式建 12 列"很可能互斥（模板占用错误 515/507） | 模板步骤失败只 WARN，主判据（全 null 列 timestamp 保留）不受影响；③④ 是代理/降级判据 |
| **CO-39** 优先级 | 排序结论（低层/新 version/文件数多/分区倒序）**一律 WARN-only**；线程族 `N_WORK==1`、`N_SUB==4` 才是硬断言 | 五级排序是**比较器实现细节**（CO-18 已观察到跨类型取值不影响本场景执行顺序）⇒ 不能升格为产品缺陷 | 排序类 WARN 属预期；若 `N_SUB != 线程数×子线程数` 而 FAIL，先确认该构建的子任务池不是懒创建/改名 |
| **CO-40** 恢复分支 | D3-7「空目标文件」用**代偿构造**（真实产物名末段+7、0 字节、无 `.resource`）；`kill -9` 的预期噪声写入本用例 BENIGN | 规格要求"配合空库"，但空库无从派生合法文件名 | D3-7 若 FAIL 需人工确认是否等价；`Execute FragmentInstance…failed`/`Failed to CHANGE_REGION_LEADER`/`RatisRequestFailedException`/`Compaction task (is )?killed` 属**注入噪声** |
| **CO-42** fast vs 默认 | D 相取"三者皆非 Fast"（模板默认实为 B 相组合）；硬判据 `BYTES_C ≥ 1.2×BYTES_D` | 跨实现字节比阈值；本环境载荷仅约 3MB，两者产物可能很接近 | **FAIL 但 correctness/文件数全过 ⇒ 先怀疑阈值偏紧**，把 D 相改成 `fast/fast/read_chunk` 只差 `inner_seq_performer` 再比 |
| **CO-41** OBJECT×TTL | object 计数用**全局增量**（表名是 base32 目录名，无法按表匹配）；A 相只断言终态按点清理 | 存储路径无表名映射 | 相间把 TTL 复位 `INF` 并用 `c41_obj_stable` 采样保证归因；B 相若报"合并未推进"，先看默认 `inner_compaction_total_file_size_threshold` 是否真的要求 ≥10 个文件（与 CO-38 的门槛结论互相印证） |
| **CO-35/37** 冻结手法 | `compaction_schedule_interval_in_ms=5000`（不是 1000） | 要"一看到首个 finishes 就热关 seq 合并"，抢在级联之前 | 仍有小概率被下一轮并掉：CO-35 有 ±region 容差，CO-37 的③/level 校验**无容差**（最可能的首跑 FAIL 点） |
| **CO-38/36** | 判据详见脚本头部注释（未在本文重复） | — | 若"门槛"断言与 CO-41 B 相结论冲突，以**同一构建上的实测**为准，并把两处结论对齐后修订判据 |

## 二、CO-43（同名序列重建 + 对齐属性翻转，IOTDB-5686）——我自己实现，自查出的两个坑

| 项 | 说明 |
| --- | --- |
| 构造要点 | 批1（非对齐）→ `DELETE TIMESERIES d1.**,d2.**` → **同名 `CREATE ALIGNED TIMESERIES`** → 批2 用 `INSERT … ALIGNED`。批2 的时间**必须晚于批1 的水位**（否则落乱序区，就不是官方 MG-P18 的"顺序空间内"场景）；同时仍在**同一时间分区**内 ⇒ 两代文件都留在 `sequence/`，靠 `candidate_file_num=2` + 分区内恰好 2 个 seq 文件被**同一任务**吃到（文件数 2→1 即证据） |
| 自查已修 2 个坑 | ① 初稿把批2 时间放在批1 **之前**（会导致整段场景退化到乱序区）→ 改成 `T0+20000`；② `show devices` 的设备单元格是**全路径** `root.co43.d1`，初稿正则 `\| *d1 *\|` 匹配不到 → 改成 `\|[^|]*[.]d1 *\|` |
| 判据取向 | 官方缺陷的表现是**行数不一致**（首测"只有 80 个点"）⇒ 判据落在"逐设备行数 + 逐点 (time,value) 指纹"上，而不是"合并完成/无报错"；另外把 `show devices` 的对齐属性列**原文打进日志**，列名未知时只 WARN（版本差异） |
| 首跑风险 | ① `show devices` 的 `IsAligned` 列名/取值格式随版本可能不同（已降级为 WARN + 记录）；② 阶段⑤ 需要 unseq 空间真的产生文件（断言 `unseq≥1`，不成立即判"场景未成立"）；③ 阶段⑥ **整集群重启**（`cluster_stop`+`cluster_start`）会让本用例偏长（约 25 min），且重启后 CLI 需要重新就绪 |


## 三、首跑建议顺序与观察点

1. **先单条跑**（避免 9 条连跑把集群状态搅在一起、也便于定位）：
   `bash tools/run_all.sh --set official --only CO-35 --ver v20121rc7_1014_7c61428`
   依次 CO-35 → CO-37 → CO-36 → CO-38 → CO-39 → CO-41 → CO-42 → **CO-43** → CO-40（CO-40 最重且注入式，放最后）。
2. 读结果按这个顺序：`results/<ID>_<runid>.out` 里的 `FAIL` 行 → 场景有效性断言是否先失败 → 再看 `results/artifact_*/` 里的 CN/DN 日志。
3. **判"用例问题"还是"产品问题"的硬标准**：
   - 场景有效性断言失败（布局/分区数/参数生效值不符）⇒ **用例/构造问题**；
   - 双信号（finishes↑ 且 TsFile↓）通过但某条判据失败，且该判据有**源码或官方文档出处** ⇒ 才可能是产品问题；
   - 排序/时序类、阈值类、代理类判据失败 ⇒ **先记 WARN/人工复核**，不直接提单。
4. 首跑后要回填的地方：`cases/cases.tsv` 的描述（若实现与描述不符）、本文件的"首跑实测"列、`docs/RESULTS.md`、`results/final_results.csv`。

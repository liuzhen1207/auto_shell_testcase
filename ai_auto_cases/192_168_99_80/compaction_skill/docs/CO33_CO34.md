# CO-33 / CO-34：未排序 TsFile 真实修复链路 + 千级 TsFile 级联压力

> 2026-10-15 新增（RC7 `v20121rc7_1014_7c61428` 批次）。两个用例都是"必须专门构造"的场景，
> 前者要造**内部时间乱序**的 TsFile，后者要把文件规模推到**千级**。

## 一、CO-33 `cases/common/co_repair_unsorted_load.sh`

### 为什么必须专门构造

`enable_auto_repair_compaction`（CO-32 已覆盖开关基础语义）只有配合**真正需要修复的文件**才能走通
修复链路。SQL 正常写入产生的 TsFile 一定是有序的，也拿不到 `NEED_TO_REPAIR_*` 状态，
所以 CO-32 只能做"不误报"的负向检查。要真跑一遍链路，必须：

1. 造一个**内部时间乱序**的 TsFile；
2. 通过 `load` 导入（load 是"外部文件进入数据区"的唯一入口）；
3. 用 `START REPAIR DATA` 触发修复扫描。

### 构造方式（对齐官方集成测试）

依据 `integration-test/src/test/java/org/apache/iotdb/db/it/IoTDBRepairDataIT.java`
（rc/2.0.12.1）：用底层 `TsFileIOWriter` + `ChunkWriterImpl` 按 **2,3,5,4** 的顺序写点，
`load` 后 `SELECT` 结果不是升序，`START REPAIR DATA` 后轮询直到恢复升序。

本 skill 的生成器 `assets/unsorted/UnsortedTsFileGen.java` 与之等价，并做两点加强：

- **值与时间一一对应**（t+2→11、t+3→12、t+5→13、t+4→14），而官方测试所有点值都是 1
  ⇒ 我们能额外断言"修复后 `(time,value)` 配对没被改错"；
- 支持 `offsetMs`/`valueBase` 两个可选参数，用来在同一目录里造出**时间范围重叠**的第二个文件（C 相）。

编译/分发：`assets/unsorted/build_gen.sh`（用服务端自带 jar `timechodb-server-2.0.12.1.jar`
编译，再把 class `scp` 到**执行节点**——`load` 读的是该 DataNode 本地磁盘上的文件）。

### 判据（全部硬断言）

| 相 | 判据 |
| --- | --- |
| A 正向 | load 后 4 行且**乱序**（场景有效性）→ `START REPAIR DATA` → 查询恢复**严格升序**、行数不变、`(time,value)` 配对不变；日志增量：`[RepairScheduler] start check tsfile` ≥1、`need to repair because …` ≥1、`RepairUnsortedFileCompactionTask` ≥1、`[RepairScheduler] Repair task finished` ≥1；**空间**：修复目标出现在**乱序区**（源码 `RepairUnsortedFileCompactionTask.generateTargetFile():144-151`）；**进度**：三节点 `system/repair/repair-data*` 存在、含 `START_TIME`、`TSFILE`（=无法修复的文件）行数为 0 |
| B 开关对照 | `enable_auto_repair_compaction=false` 且**不显式触发** → 60s 静默窗口内既要保持乱序、又不得出现修复任务（不静默修复）；随后**显式** `START REPAIR DATA` → 仍然修复成功（源码 `StorageEngine.repairData():695` 只判只读与并发，不受该开关影响 ⇒ 该开关只影响"自动选择"路径） |
| C 观察 | 两个时间范围重叠的 seq 文件 + 打开 seq 合并（auto_repair=false）→ **记录**是否出现待修复判定 / `CompactionValidationFailedException`（源码 `AbstractCompactionTask:543-557`）；随后显式修复 → 断言**重叠文件被移出顺序区**（unseq ≥1、seq 下降；实现是硬链接 `FileUtils.createLink`） |
| D 重复时间戳 | 生成器 `mode=dup`（t=+2,+3,+3,+5）—— 对应官方设计文档错误类型①的"**重复**"分支。**修复语义 = 排序 + 去重**（设计文档 L94「…排序并去重后写入目标文件」+ 实现 `RepairUnsortedFileCompactionWriter.endMeasurement():67-84`「remove duplicate timestamp and sort」）⇒ 判据：时间列非降、**修复后行数 = 修复前不同时间戳个数**（4 个点含 1 个重复 ⇒ **3 行**，不是 4 行）、**修复后时间集合 = 修复前时间集合**（不丢任何不同时间戳）、修复前**唯一**时间戳的 `(time,value)` 配对原样仍在、修复后所有配对 ⊆ 修复前配对集合（不得凭空造值/错配）、走修复链路；并把修复后的时间列与配对打进日志 |
| E Page 间乱序 | 生成器 `mode=pages`（p1=[+2,+4]、p2=[+3,+5]，页内有序但跨页乱序）—— 对应错误类型②；修复后恢复严格升序、`(time,value)` 配对不变、走修复链路 |

**官方 4 类错误覆盖情况**：①页内乱序 → A；①页内重复 → D；②Page 间乱序/重叠 → E；④顺序文件间 resource DeviceTimeIndex 重叠 → C；
**③Chunk/Page 统计信息错误未被用例覆盖**（文件统计由写入器即时计算、`.resource` 为二进制，需要"改造二进制/构造历史版本文件"才能造，属"专门构造仍未解决"的项，如实记录）。

### 修复链路源码依据（RC7 源码树 `D:\IDEA\timechodb_src\v20121`）

- `StorageEngine.repairData():695-706` → `UnsortedFileRepairTaskScheduler(dataRegionList,false)`；`recoverRepairData():730-755` 是"上次没修完"的恢复入口。
- `UnsortedFileRepairTaskScheduler`：`repairTaskTime` 取自 repair 日志（为空则当前时间），
  `RepairTimePartition.resourceTimestampFilter()` 只扫描**该时刻之前**已存在的文件 ⇒ 先 load 再 `START REPAIR DATA` 的顺序是必须的。
- `RepairTimePartitionScanTask:83-142`：对每个文件 `new RepairDataFileScanUtil(f).scanTsFile(true)`，
  `hasUnsortedDataOrWrongStatistics()` 为真 ⇒ 置 `NEED_TO_REPAIR_BY_REWRITE` + 打
  `[RepairScheduler] {} need to repair because it has internal unsorted data` + 提交 `RepairUnsortedFileCompactionTask`。
- `RepairDataFileScanUtil:358-437`：逐页解码时间列并 `checkPreviousTimeAndUpdate` —— `previousTime >= time` 即抛
  `CompactionLastTimeCheckFailedException`（**这就是"内部乱序"的判定点**）；另有一条"文件统计与真实数据不符"的分支
  `compareDeviceTimeRange`。
- 官方语句：`START REPAIR DATA` / `STOP REPAIR DATA` / `SHOW REPAIR DATA PARTITION TABLE PROGRESS`（`StartRepairDataStatement`）。

## 二、CO-34 `cases/common/co_scale_cascade.sh`

### 目的

既有用例的文件规模只有 3~6 个（CO-01/02），看不出**层级合并**是否真的级联（L0→L1→L2…），
也压不出资源类问题。本用例把规模推到**千级**。

### 做法

1. 三类合并全关（`CMP_EXTRA_WRITE`）；一次 CLI 会话连续执行 N 轮 `INSERT 1 行 + FLUSH`
   （`use` + 循环生成语句文件后 `cat | session_tree`，`SQL_TIMEOUT_SEC` 按规模放大）
   ⇒ 每个 DataNode 得到 N 个 level-0 seq TsFile；
2. 等异步 close 落盘（轮询 `minL0` ≥ 90% × N，上限 180s）后记基线：TsFile 数、层级分布、
   指纹（`cmp_fp_tree`）、`finishes`、卡死线程（`cmp_stuck_sum`）；
3. 热开 seq 合并（`inner_compaction_candidate_file_num=30`，让层级快速推进），
   每 15s 记录层级分布演进，直到文件数收敛到 `max(20, N/20)` 或窗口（默认 1500s）超时。

### 判据

- `finishes` 必须增加（合并确实推进）；
- TsFile 数必须下降；收敛到目标（否则 WARN 记录）；
- **最高层级 ≥ 2**（证明"级联"而不是只做了 L0→L1）；
- 合并前后**数据指纹不变**、行数不变；
- 无卡死合并线程（`cmp_stuck_sum=0`）；
- 收尾三件套（sync lag → 逐 DN 副本一致性 → CN/DN 日志异常）全绿。

### 运行

```bash
V_TESTDB=v20121rc7_1014_7c61428 BUILD_TAG=v20121rc7_1014_7c61428 \
  bash cases/common/co_scale_cascade.sh --consensus IoTConsensus
# 或： bash tools/run_all.sh --set scale --ver v20121rc7_1014_7c61428
```

可调：`C34_FILES`（默认 1000）、`C34_CAND`（默认 30）、`C34_WIN`（默认 1500s）。

**源码复核（设计 vs 实现，避免把设计要求当实现行为）**：

- `RepairUnsortedFileCompactionTask.generateTargetFile():144-151` 明确写了
  `if sourceFile.isSeq() ⇒ targetFileDir 的 "sequence" 替换为 "unsequence"`
  ⇒ 设计文档"目标写入乱序空间"在 RC7 **确实如此实现**，因此可作**硬断言**。
- 但 `RepairTimePartitionScanTask:135` 传的 `sequence` 参数是 `sourceFile.isSeq()`，
  即"乱序源文件的目标仍在乱序区"——所以 **unseq≥1 硬断言只对 sequence 源文件成立**（A/C/D 三相的源都是 load 进顺序区的文件，成立）。
- `RepairUnsortedFileCompactionTask.calculateRepairMethod():204-223`：`NEED_TO_CHECK` 文件先扫描，
  乱序/统计不符 ⇒ `NEED_TO_REPAIR_BY_REWRITE`；否则 `isSeq()` ⇒ `NEED_TO_REPAIR_BY_MOVE`（硬链接移动），
  unseq 源 ⇒ 复位 `NORMAL`。
- `getEstimatedMemoryCost():226-243`：内存估计超限 ⇒ `CAN_NOT_REPAIR` + WARN（日志
  `STORAGE_LOG_REPAIRUNSORTEDFILECOMPACTIONTASK_CAN_NOT_REPAIR_UNSORTED_48124B0C`）——
  若用例出现"修不动"，先查这条日志。

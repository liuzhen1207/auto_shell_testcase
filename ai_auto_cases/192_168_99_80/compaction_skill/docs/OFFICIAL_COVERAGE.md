### 0.3 判定口径（避免把数字读大）

- **场景要素 vs 环境规模**分开看。官方文档是 **1C1D / 1C3D / standalone + iot-benchmark + GB~TB 级历史备份 + 跨版本（master 0224/0302/0305、rc/1.1.0 0306/0314/0321/0323）性能对比**的记录；
  现有 43 条是 **3C3D 三副本 + SQL 直写 + 分钟级**的自动化用例。「已覆盖」按**场景要素与判据是否等价**判定，
  规模/环境/跨版本差异一律写进「缺口说明」。
- **覆盖强度**：`完全`（场景要素 + 判据等价）／`部分`（核心要素命中但有明确缺失）／`仅间接`（只有相邻场景旁证）／`未覆盖`。
- 每条判定都给出**依据**：`cases.tsv` 说明原文片段，或**脚本头注释里的判据原句 + 源码位置**。

#### CO-39 · 任务优先级排序规则与线程族数量关系（D2-9/D2-10/D2-11 + MG-T01/T02/T03）

| 项 | 内容 |
| --- | --- |
| 脚本 | `cases/common/co_priority_rules.sh` |

7. **附加（MG-T01/T02/T03）**：每个 DN `jstack` 后计数

   `N_WORK = jstack | grep -c 'IoTDB-Compaction-Worker'`、
   `N_SUB = jstack | grep -c 'IoTDB-Compaction-Sub-Task'`。

- ① 双信号（每段）：`finishes` 增加 **且** `cmp_all_sum` 下降；`cmp_fp_tree` 不变；

- ③ 段 2：先启动任务的源文件 maxVersion 更大；
- ④ 段 3：文件数多的任务先启动；
- ⑤ 段 4：较新时间分区的任务先启动；
- ⑥ **附加线程族**：`N_WORK == compaction_thread_count (1)`（CO-23 回归）；

#### CO-40 · 合并执行的临时态与恢复四分支 + 残留文件/句柄（D3-1/3-2/3-3/3-4/3-5/3-7/3-9）

| 项 | 内容 |
| --- | --- |

**构造步骤**

2. `DELETE FROM root.corec.d1.** WHERE time <= T1`（删一部分行，**制造 `.mods`**）；记 `MODS0=$(cmp_mods_sum root.corec)`、`cmp_all_sum`、`cmp_lay`、`cmp_fp_tree`、`ROWS0`（删除后的行数）。

7. **恢复分支 D3-7（空目标文件）**：`root.corec3` —— 合并完成后手工造一个 0 字节的 `.tsfile`（配合空库），重启 → 断言被清理。
8. 全部相结束后：`cmp_mods_sum`、`cmp_tmp_leftover`、`cmp_all_sum`、`cmp_lay`、`cmp_fp_tree`、`ROWS`、deleted 句柄 60s 后再采一次。

**判据**
- ① **临时态（D3-1）**：合并进行中**存在**不以 `.tsfile` 结尾的临时目标文件；合并完成后**必须消失**（`cmp_tmp_leftover == 0`）；
- ② **mods 迁移（D3-2/D3-3）**：`MODS0 > 0`（场景有效性）⇒ 合并完成后**无孤儿 `*.mods`**（每个 `.tsfile` 的 mods 数与目标文件数对齐），且被删行的行数 `ROWS` 保持（删除不复活）；
- ③ **恢复回滚（D3-5/D3-9）**：重启后**不续合** ⇒ 出现**新的** `task starts`（`cmp_inner_start` 相对重启后基线增加），且目录里**无** `*.compaction.log`/`*.compaction.mods`/不以 `.tsfile` 结尾的临时文件；`cmp_fp_tree` 与崩溃前**完全一致**；
- ④ **日志不完整（D3-4）**：截断日志后重启**不报错**、不阻塞后续合并（之后仍能 `task starts` 并完成）；
- ⑤ **空目标文件（D3-7）**：0 字节 `.tsfile` 在重启/下一轮后被删除；
- ⑥ **句柄与 fd（官方 MG-P15/P16）**：合并完成后 **+60s** 每个 DN 的 `lsof deleted` 计数 ≤ 合并前基线 + 2，且 +30s 与 +60s 相同（已稳定）；`/proc/<pid>/fd` 总数不持续增长；
- ⑦ 三副本一致 + `cmp_stuck_sum=0` + 收尾三件套（`kill -9` 期间 `Execute FragmentInstance … failed` 计入 BENIGN）。

**场景有效性断言**：① 开合并前 `cmp_min_l0 ≥ 2`；② 崩溃前**确实**有 ≥1 条该库 `task starts with`；③ 重启后立刻的 `cmp_all_sum ≥` 崩溃前基线（证明当时合并**未完成**，否则退化为 CO-29 ④）；④ `MODS0 > 0`。

#### CO-41 · 表模型 OBJECT 类型合并与 TTL/deletion 清理语义（D7-1/7-2/7-3/7-4）

| 项 | 内容 |
| --- | --- |
| 脚本 | `cases/common/co_object_ttl.sh` |
| 覆盖 | D7-1~D7-4（OBJECT 仅存引用、**只清理 TTL 过期的 object 文件、不清理 deletion 删除的**、fully dirty 文件删前清理、逐点扫描删 object）；官方文档**未覆盖**（V2.0.8.1 新特性） |

**构造步骤**（表模型：`create table` + `OBJECT` 列，OBJECT 值用 `to_object(true, 0, X'...')` 写入）
1. `root.coobj`：`create database root.coobj;` → `create table root.coobj.t1 (dev STRING TAG, t INT64 FIELD, o OBJECT FIELD);`（具体 DDL 以现场 `metadata_skill/docs/DDL_INVENTORY.md` 的表模型语法为准）。
2. `cmp_compaction_off`；写 **3 批** OBJECT 值（每批 200 行、每行一段可区分的小二进制），逐批 `cmp_wait_close`；`flush`。
3. 记基线：object 目录下的真实文件数（`find <dn_data_dir>/.../object -type f | wc -l`，路径以现场为准）、`cmp_all_sum`、`cmp_mods_sum`、表行数与 OBJECT 列可读性（`select count(o)`）。
4. **A 相（TTL 过期）**：`ALTER TABLE root.coobj.t1 SET PROPERTIES ttl='30s'` → 等数据过期 + settle 合并（复用 CO-13/CO-14 的 settle 判定方式）→ 断言 object 真实文件数**下降**、TsFile 数下降。
5. **B 相（deletion，无 TTL）**：独立库 `root.coobj2` → 同样 3 批 → `DELETE FROM root.coobj2.t1 WHERE time <= T`（删一部分）→ 触发合并 → 断言 object 真实文件数 **不因 deletion 下降**（**D7-2 的核心对照**）。
6. **C 相（fully dirty）**：独立库 `root.coobj3` → TTL 设为极小值使**整个 TsFile 全过期** → settle 直接删 TsFile → 断言 object 真实文件在 TsFile 被删前已被清理（object 文件数降到 0，且无残留引用）。

**判据**
- ① 双信号：`cmp_seq_inner_finish` / `SettleCompaction task starts` 增加 **且** `cmp_all_sum` 下降；
- ② A 相：object 真实文件数**下降**；表 `select count(o)` 与 TTL 过滤后的期望行数一致；
- ③ B 相：**object 真实文件数不变**（D7-2：deletion 不清理 object）；被删行 `count` 正确；
- ④ C 相：fully dirty 文件的 object 文件在 TsFile 删除前被清理 ⇒ 终态 object 文件数 = 0 且 TsFile 数 = 0；
- ⑤ 合并前后 OBJECT 值可读且能取回原始二进制（D7-1）；
- ⑥ `ttl_check_interval` 的生效方式按 D7-6 断言为 **restart-only**（`cmp_set_hot` 返回需要重启、`cmp_eff` 值不变）；
- ⑦ `cmp_stuck_sum=0` + 收尾三件套。

**场景有效性断言**：A/B/C 三相在写入后都要断言 `object 真实文件数 > 0`（否则场景没造出来）；B 相必须断言「**没有设置 TTL**」（`SHOW TABLES` / `information_schema` 里 ttl 为 INF）。

> **诚实标注**：OBJECT 的存储路径与 DDL 细节依赖现场版本（V2.0.8.1 特性）；若 RC7 的表模型 OBJECT DDL/路径与设计文档不符，
> 本用例应**先做能力探测**（`metadata_skill/docs/DDL_INVENTORY.md` 的方法），探测失败则整体判"场景不可构造"并如实记录。

| **历史缺陷产物 / 竞态** | MG-P05（IOTDB-5706 重启前后查询不一致、ratis ERROR、`305` 报错、刷 metadata 慢）、MG-P16（IOTDB-5671 的**缺陷版本**句柄不释放）、FC-13 问题1（IOTDB-5210：`FileReaderManager` Map 含已关闭 `TsFileSequenceReader`，close/init 竞态）、FC-13 问题2（IOTDB-5165：**`TsFileResource` 从 deviceTimeIndex 降级为 FileTimeIndex** 时误报 overlap） | 需要"缺陷版本 + 特定历史 `.resource`/索引降级产物"或竞态；RC7 上只能做**正向**断言（如 CO-40 的"无残留句柄"），无法复现缺陷本身 |
| **需要 benchmark 专有产出** | MG-09（`fit1_2_3_4_51个时间分区.xlsx`、TIMECHODB-81 confignode 退出） | 依赖 benchmark 客户端行为与特定构建 |

### 6.3 关于「部署形态」的说明（不单独计为不可构造）

官方文档 A/B 的绝大部分场景是 **1C1D / 1 副本（ratis/ratis/IoT）/ 单机版 standalone**；
本环境固定 **3C3D + RF=3 + IoTConsensus**。差异体现在：
- 三副本下**每批 flush 后各副本的 close 时刻不同**（CO-17 第 2 轮事故 18 的根因）⇒ **每批写完必须等该库 close 事件数达标**再写下一批，这是本环境造场景的硬要求；
- 单机版的文件数/层级是唯一真值；3C3D 下必须先断言**各副本布局一致**，再谈合并推进（CO-17 事故 18 的做法）；
- 副本引入了单机版没有的高可用维度（DT-08 磁盘只读、DT-09 节点下线已覆盖）。
⇒ **不**把 1C1D 场景判为不可构造，而是全部按 3C3D 重述判据。

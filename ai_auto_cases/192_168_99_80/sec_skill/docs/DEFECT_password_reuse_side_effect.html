一、需求原文（摘要）

《V2.0.7.1-安全模块-身份鉴别-强安全级别密码-需求分析》V0.2（2025-10-23）：

在 iotdb-system.properties 中增加配置项 password_reuse_interval_days，默认值为 0（代表无历史密码约束）；当设置值大于 0 时，用户修改密码后将对旧密码进行记录与匹配，若新密码与某一历史密码相同、且该历史密码最后一次修改时间至今小于该配置值，则拒绝并报错 The password has been used recently, and it cannot be reused before <下次可用时间>。

配置模板 iotdb-system.properties.template:2297 亦为 password_reuse_interval_days=0。

二、环境

  1. 版本：TimechoDB V2.0.13.1，BuildInfo 83183d0（企业版，ACTIVATED）。
  2. 集群：3 ConfigNode + 3 DataNode（192.168.99.77/78/79），SchemaRegion 3 副本 / DataRegion 3 副本，IoTConsensus。
  3. 驱动：192.168.99.80，start-cli.sh；普通模式（root）与三权分立模式（security_admin）均验证。

三、复现步骤（约 1 分钟）

前置说明（关键）：不显式设置该配置项（conf 中没有该键）时没有问题，A→B→A 可成功；本缺陷只在显式配置为 0 时触发。

# 1) 在 conf 中显式写入 0（或执行 SET CONFIGURATION 'password_reuse_interval_days'='0'）
#    iotdb-system.properties: password_reuse_interval_days=0
# 2) 确认生效值
show configuration;                     -- 回显 0

# 3) 建用户（密码 A）→ 改成 B → 再改回 A
create user u1 'Abcdefgh123!';
alter user u1 set password 'Abcdefgh456@';
alter user u1 set password 'Abcdefgh123!';

四、实际现象 vs 期望

期望：第 3 步成功（0 = 无历史密码约束）。

实际：第 3 步被拒，且窗口恰为 1 天：

701: The password has been used recently, and it cannot be reused before Tue Nov 17 16:09:46 CST 2026

（提示时间点 = 密码 A 最后修改时间 + 1 天 ⇒ 实际生效窗口 1 天，而非 0）

五、对照实验（定位到"0 被改写为 1"）

配置show configuration 回显A→B→A 结果结论
conf 中无该键（干净默认）不列出该键成功默认路径正常（与用户复核一致）
显式 =00701 拒绝（1 天）与需求冲突（本缺陷）
显式 =-1（代码默认值）-1成功禁用语义正常
显式 =11窗口内拒绝、窗口外允许符合需求

补充：将 conf 写 0 并整集群重启后仍拒绝（排除热加载/缓存）；-1 放行、0 拒绝，两者仅差 setter 对 0 的处理 ⇒ 根因唯一。

六、根因（源码级，确定性）

iotdb-core/node-commons/src/main/java/org/apache/iotdb/commons/conf/CommonConfig.java:3428

public void setPasswordReuseIntervalDays(long passwordReuseIntervalDays) {
  this.passwordReuseIntervalDays = passwordReuseIntervalDays == 0 ? 1 : passwordReuseIntervalDays;
}
  • 任何来源的 0（conf 文件、SET CONFIGURATION ... '0'）都会被改写成 1；
  • 启动加载（IoTDBDescriptor.java:1196）与热加载（IoTDBDescriptor.java:2880）都会经过该 setter，因此重启也无法恢复；
  • 消费侧本来就把 <=0 当禁用：DataNodeAuthUtils.verifyPasswordReuse()（DataNodeAuthUtils.java:186-206）中 passwordReuseIntervalDays <= 0 直接 return ⇒ setter 的 0→1 改写多余；
  • 对照：setPasswordExpirationDays() 走 EditionGate.forceValueInIoTDB(...)，没有 0→1 改写（CommonConfig.java:3418），说明这不是统一约定。

七、影响

  1. 显式 0 不可用：需求规定 0 = 无约束，但写 0 得到 1 天限制；模板本身即写 0，照模板/文档配置的用户会命中。
  2. 配置展示与真实行为不一致：show configuration 显示 0、实际按 1 天判定，运维无法通过配置关闭，排障易被误导（本次排查即因此耗时）。
  3. 运维可用性风险：变更失败需回滚到原密码时，24h 内会被拒。
  4. 策略偏严而非绕过，不构成安全漏洞；属功能与需求不符。优先级 P3。

八、修复建议

  1. 最小修复（推荐）：this.passwordReuseIntervalDays = passwordReuseIntervalDays;（去掉 == 0 ? 1）。消费侧已有 <=0 早退，行为即符合"0/-1 = 不限制、>0 = N 天"。
  2. 若产品认为"0 最少按 1 天"是刻意设计：应修改模板与文档（模板不要写 0，或注明"0 视作 1 天"），并让 show configuration 显示生效值而非文件值。
  3. 补单测：set(0) 后 get()==0；默认配置启动后 A→B→A 成功；>0 窗口内拒绝/窗口外允许；show configuration 与实际判定一致。

九、验证方法（修复后）

  1. conf 无该键（默认）：A→B→A 必须成功（当前已成功，回归保护）；
  2. SET CONFIGURATION 'password_reuse_interval_days'='0' 后立即 A→B→A 必须成功（当前被拒）；
  3. =1 时窗口内必须被拒（文案带 +1 天时间点），时钟前移 2 天后必须成功；
  4. show configuration 回显值 = 实际判定值。

回归用例：sec_skill 的 SEC-05（cases/password/sec_password_reuse.sh）。按"两级判定"实现：默认/-1/=1 为硬门禁，显式 0 仅记录 WARN；修复后该 WARN 自动转 PASS。

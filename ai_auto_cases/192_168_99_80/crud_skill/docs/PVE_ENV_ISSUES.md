## 二、用例在 PVE 上失败、本地干净 3C3D 不复现

### 2.1 CR-01 时间戳精度（TimechoDB-11025）

| 项 | PVE | 本地同 build（`v20131rc2_1110_83183d0`） |
| --- | --- | --- |
| 结果 | FAIL fail_flag=2 | **PASS fail_flag=0（857s）** |
| 失败点 | 停 10.13.0.190 后经 .181 / .197 查询，`.987852987Z|1` 这一行**出现两次** | 逐副本停 DN 比对全部一致 |

PVE 失败原文：
```
FAIL 停 10.13.0.190 时经 10.13.0.181 查询 与基准不一致:
     基准 [.987852987Z|1, .000000000Z|3]
     实得 [.987852987Z|1, .987852987Z|1, .000000000Z|3]
```

可能原因（待平台确认）：
1. 该实例在本次执行前**已跑过 CR-01**（我在 22:12 kill 过一次 CR-01 之前的批次，CR-02 那次运行被 kill），
   同一库名 `root.crts*` 的**残留数据**与本次写入混在一起，导致查询多出一行；
2. 停 DN 后副本未收敛（flush 未完成）就查询；
3. 实例数据目录未清理（用例本身不 `DROP DATABASE`，见第三节）。

### 2.2 CR-09 Mod 生命周期（TimechoDB-11092）

| 项 | PVE | 本地同 build |
| --- | --- | --- |
| 结果 | FAIL fail_flag=3 | FAIL fail_flag=1，但**失败点不同**（合并未推进，没走到重启断言） |
| 关键现象 | 重启后既有 `.mods2` 从 **35B 变 70B**、md5 变化；各副本 `.mods2` 数 1→2；d2 行数 100（期望 0） | 纯 V2 路径最小复现：重启前后 `.mods2` **完全不变**（35B，md5 相同） |

PVE 日志（同一次运行内）：
```
[重启前] 1794970437352-1-0-0.tsfile.mods2 size=35B md5=9de6b670…  .mods2 总数=1
--- ④ 重启集群（完整 stop → start，数据不清）---
[重启后] PASS V1 旧 Mod 文件已被升级为 V2（出现 1794970460503-…mods2、旧 .mods 消失）
         FAIL R-28：旧 Mod 记录生效 ⇒ d2 行数 100（期望 0）
         1794970437352-1-0-0.tsfile.mods2 size=70B（原 35B）md5=c7ecaac1…
         .mods2 数：1 → 2
```

**这是一个值得研发看的现象**：V1→V2 升级时，**已存在的 V2 `.mods2` 被追加了一遍**（35→70 字节），
而本地"纯 V2 路径"（无 V1 `.mods` 需要升级）最小复现中不会发生。
⇒ 怀疑点在 **V1→V2 mod 升级逻辑对已有 `.mods2` 的幂等性**，而不只是环境脏。
建议：研发用同一用例（CR-09）在干净 3C3D 上复跑，或在 PVE 上重跑一次 CR-09，确认 35→70 是否稳定出现。

### 2.3 CR-07 删除中间态（TimechoDB-11090）

失败点不是产品行为，而是**用例场景构造失败**：
```
[root.cr07b] 写入后：可查行数=250 期望=12000；TsFile 数=0 → 1
FAIL [root.cr07b] 场景有效性：大 payload 全部可查（数据在 memtable）: 实际=[250] 期望=[12000]
WARN [root.cr07b] flushing 相场景未成立 ⇒ 写入过程中已被自动 flush（本构建按内存压力触发）
```
⇒ 用例依赖"11MB 数据留在 memtable 不落盘"，但 2.0.13.1 默认 memtable 阈值更小，写入过程中已 flush。
**不是产品问题**，需要调大 `memtable_size_threshold` 或减小 payload 后重跑。

## 三、为什么"实例不干净"会放大问题（用例侧因素）

我查了几个用例：**它们都不 `DROP DATABASE`**（CR-09 中 `DROP DATABASE` 出现 0 次），用的是**固定库名**：

| 用例 | 固定库名/文件 | 是否清库 |
| --- | --- | --- |
| CR-09 | `root.crlife`，`.mods2` 断言到具体文件名/字节数/md5 | 否 |
| CR-01 | `root.crts*`（按相位切换） | 否 |
| CR-07 | `root.cr07b`、`root.cr07c` | 否 |
| CR-04/05/06 | 各自固定库（mods2 相关） | 否 |

⇒ 如果 PLM 实例**复用了上一次执行的数据目录**，前一次留下的同名库/`.mods2` 文件会直接污染后一次断言
（尤其 CR-09 这种"断言具体文件的字节数/md5"的用例，对残留极其敏感）。

本地跑同样用例前，我这边往往是"清库重建"（`rm -rf data` 或框架重建），所以本地更干净。

## 四、建议

**平台侧**
1. 确认每次执行是否 **`rm -rf /opt/timecho/<ver>/data`**（或从模板快照重建盘）；从现象看至少有一次被复用了；
2. 修复 P2（被 kill 的运行要回收槽位/实例）与 P1（502）；
3. 长跑用例（CR-10 类）提高 deadline 或允许单独模板。

**用例侧（我这边可改）**
1. 每条用例开头加"清理本用例库"（树模型 `DROP DATABASE <db>` 忽略 508；表模型 `DROP DATABASE IF EXISTS`）；
2. 关键断言不要依赖具体文件名/固定字节数（CR-09 已按需求写成 md5/字节数，可改为"结构+数量+语义"断言）；
3. CR-07 改成先调大 `memtable_size_threshold` 再构造 flushing 相。

**验证方式**
- CR-01：在 PVE 上重跑一次（干净实例），若 PASS 则确认是脏数据；
- CR-09：在 PVE 上重跑一次，若仍 35→70，则**按产品缺陷处理**（V1→V2 升级重复追加），我可进一步用最小脚本注入 V1 `.mods` 复现。

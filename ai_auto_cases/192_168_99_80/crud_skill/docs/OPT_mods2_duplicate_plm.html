一、问题概述（代码优化类）

DataNode 重启恢复时，如果同一个 DataRegion 内**存在 V1 旧格式 `.mods` 文件**（需要做 V1→V2 升级）， 升级流程会把该 region 内**已经存在的 V2 `.mods2` 文件**再写一遍，导致同一份删除记录重复、Mod 文件体积翻倍。

不影响数据正确性（删除语义仍生效、查询结果正确），属于文件冗余/幂等性优化； 但会让"Mod 文件持久性/幂等"类校验误判，长期多次升级场景存在体积放大风险。

二、环境

  • 版本：TimechoDB V2.0.13.1，BuildInfo 83183d0
  • 集群：3C3D（3 ConfigNode + 3 DataNode），SR=3/DR=3，IoTConsensus
  • 发现方式：CR-09（Mod 生命周期用例，PVE 执行）失败 → 本地干净 3C3D 最小脚本复现

三、复现步骤（最小，必现）

  1. 写设备 d2 的数据 → flush ⇒ 得到 TsFile A（有 .resource、无 .mods2）；
  2. 写设备 d1 的数据 → flush ⇒ 得到 TsFile B；
  3. DELETE FROM root.moddup.d1.** WHERE time <= 1800000000000 → flush ⇒ B 生成 .mods2（35B，1 条删除记录）；
  4. 给 A 注入 V1 文本 Mod 文件（模拟旧版本遗留）： 
    DELETION,root.moddup.d2.s1,0,1600000000000,1900000000000   >  <A>.tsfile.mods
  5. 重启集群（stop → start，**不清数据**）。

五、补充观察

  • 再重启两次不会继续增长（70B 保持 70B）⇒ 只在"升级那一趟"重复写一次，不是每次重启都写；
  • 日志中同一 region 出现两次 new single thread pool: root.moddup-13-UpgradeMod（14:39:59 与 14:40:40）， 与"升级触发两趟"一致；
  • PVE 上 CR-09 用例（TimechoDB-11092）现象完全一致：1794970437352-….mods2 从 35B → 70B、md5 变化、 .mods2 数量 1 → 2。

六、疑似根因（供参考）

  1. 升级的预期是：**只对"有 .resource 但没有 <tsfile>.mods2"的 TsFile 调用 upgradeModFile()**； 实测表明 region 内只要存在一个 V1 .mods，升级遍历时对**已有 .mods2 的文件**也执行了写 Mod 动作；
  2. 写入方式疑似**追加**而非截断重写（同一份条目写入两遍）；
  3. UpgradeMod 线程池在同一 region 出现两次初始化，可能对应两处触发点。

七、优化建议

  1. upgradeModFile() / ModFileManagement.recover() 增加"已有 .mods2 → 跳过"的判断；
  2. 写 .mods2 的 writer 使用 truncate 语义（或先判断文件是否已存在且内容完整）；
  3. 升级任务对同一 region 只触发一次（核对两个线程池的初始化点）；
  4. 补单测：构造"同 region 内一个 V1 .mods + 一个已有 .mods2"→ 重启 → 断言已有 .mods2 的字节数与 md5 不变（幂等）。

八、验证方式（优化后）

  • 重跑最小复现脚本：重启前后 B 的 .mods2 大小/md5 必须**完全一致**；
  • 回归用例：crud_skill 的 CR-09（PLM：TimechoDB-11092）应转为 passed（其"持久性：字节数/md5 不变"断言即针对此行为）；
  • 确认数据面：删除语义不变（d1 查询 0 行）、三副本一致。
